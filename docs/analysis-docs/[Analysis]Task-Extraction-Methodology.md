# [분석] 태스크 추출 방법론 적합성 평가

**문서 ID:** ANL-FINFRIENDS-TASK-001

**개정 버전:** 1.0

**날짜:** 2026-08-26

**대상:** TASK-FINFRIENDS-MVP-001 (`docs/plan-docs/[TaskList]FinFriends-Task-List.md`) · 태스크 **68건**

**수치 재현:** `python3 tools/analyze_tasks.py`

> **이 문서가 답하는 것** — 태스크 68건이 **어떤 기준으로 쪼개졌고, 그 기준을 실제로 지켰는가.** 지키지 못한 곳은 그것이 결함인지 방법론의 오해인지 구분한다.

---

## 1. 방법론 — 4단계 추출

태스크는 임의로 나눈 것이 아니라 **네 단계 순서로 추출**했다. 각 태스크의 `유형` 열이 그 단계를 나타낸다.

| 단계 | 무엇을 뽑나 | 유형 | 왜 이 순서인가 |
| :-: | --- | --- | --- |
| **Step 1** | **공유 계약과 데이터 모양** | `Contract` · `Data` | 두 태스크가 같은 계약을 다르게 구현해도 탐지되지 않는 사고를 막는다 |
| **Step 2** | **동작** — 조회 · 상태 변경 · 화면 | `Read` · `Write` · `UI` | 계약이 정해진 뒤라야 각자 구현해도 어긋나지 않는다 |
| **Step 3** | **수용 기준의 실행 가능한 대응물** | `Test` | AC가 문서에만 있으면 검증되지 않는다 |
| **Step 4** | **비기능** — 배선 · 게이트 · 관측 · 비용 | `Infra` · `NFR` | 기능이 있어야 관측할 대상이 생긴다 |
| — | 디자인 | `Design` | 개발 단계와 축이 다르다 (Part B) |

## 3. 평가

### 3.1 ✅ Step 1이 실제로 앞서 있다

**비중은 10%로 작지만 위치가 맞다.** Step 1 태스크 7건 중 **3건이 임계 경로 위**에 있다.

```
INF-001 → INF-003 → DAT-001 → CTR-001 → CTR-002 → STR-001 → …
                     ▲          ▲         ▲
                     Step 1 3건이 임계 경로를 지난다
```

계약이 뒤로 밀리면 이 사슬 전체가 밀리므로, **구조적으로 앞설 수밖에 없게** 배치돼 있다. 비중이 아니라 이것이 판정 기준이다.

### 3.2 ⚠️ 「단계 역순」 12건 — 위반이 아니라 부트스트랩

선행 태스크의 단계가 후행보다 **뒤인** 쌍이 12건 나온다.

| 후행 | 선행 | 성격 |
| --- | --- | --- |
| INF-002(UI) · DAT-001(Data) · PTN-001(Write) | INF-003 · INF-001(Infra) | 앱·DB가 없으면 아무것도 못 만든다 |
| DAT-002 · NTF-002 · ANA-002(Data·Write) | TEC-002(Infra) | 배치 진입점이 있어야 배치 작업을 얹는다 |
| NTF-001 · ANA-003(Write) | INF-004(Infra) | PWA 구성 위에 푸시·오프라인 큐가 선다 |
| TST-003 · TST-005(Test) | SEC-002 · REL-002(NFR) | 검증 대상이 있어야 검증한다 |
| STR-005(Write) | STR-004(NFR) | 분리선 게이트가 먼저 서야 확장이 안전하다 |
| **MCK-001(Data)** | **INF-002(UI)** | 목 픽스처는 **앱 골격과 토큰 위에서** 만든다 — 화면이 부르는 인터페이스를 실제 모듈 경계와 맞춰야 하기 때문 |

**결함이 아니다.** 방법론의 단계는 **추출 순서**(무엇을 먼저 식별하는가)이지 **실행 순서**가 아니다. Step 4의 `Infra` 는 성격상 **부트스트랩**이라 실행에서는 맨 앞에 온다.

> 이 구분을 놓치면 「Infra를 Step 1로 옮기자」는 잘못된 교정을 하게 된다. 그러면 *계약보다 배선을 먼저 식별하는* 방법론이 되어 3.1의 이점을 잃는다.

### 3.3 🔴 Step 3의 밀도가 높다 — Test 5건이 AC 51건을 담당

| Test 태스크 | 담당 범위 |
| --- | --- |
| TST-001 | 계약 스냅샷 · 열거형 회귀 |
| TST-002 | 별 정합성 · 멱등 · 소급 (불변값 2종) |
| TST-003 | 규제 상수 자동 테스트 — α 게이트 조건 |
| **TST-004** | **수용 기준 51건 전건 매핑** |
| TST-005 | 성능 · 부하 |

**TST-004 하나가 51건을 진다.** 태스크 하나로 두기엔 크고, 실패 시 어디까지 됐는지 보이지 않는다.

**판정** — 지금은 유지한다. 쪼개려면 **무엇을 기준으로 쪼갤지**가 먼저인데, AC는 요구사항에 걸려 있어 Epic별로 나누면 51건이 17조각이 되고 각 조각이 너무 작다. 대신 **TST-004의 실행 계획에 「미커버 AC 0건」 검사를 넣어** 진척을 셀 수 있게 했다.

### 3.4 ⚠️ Write 29건이 Step 2의 78%

상태 변경 태스크가 몰려 있다. 이것이 **백엔드 레인 병목의 원인**이다(압축안 §3.1 — 공수 141d 중 대부분).

**쪼개지 않은 이유** — Write 태스크는 대부분 **하나의 서버 진입점**에 대응한다(반영판 §6.1의 19개 진입점). 더 쪼개면 진입점 하나를 두 태스크가 나눠 갖게 되고, 그때부터 계약이 흔들린다. **경계가 진입점이므로 그보다 잘게 나누지 않는다.**

### 3.5 ✅ UI를 Write에서 분리한 것이 균형을 잡았다

`UI` 6건을 `Write` 에서 떼어냈다. 담당자와 리뷰 관점이 다르고, **UX 구현 진척을 독립적으로 추적**해야 하기 때문이다.

분리하지 않았다면 Write가 35건(Step 2의 95%)이 되어 진척이 뭉개진다.

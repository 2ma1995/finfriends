## 1. 이 프로토타입의 성격

**버리는 프로토타입이 아니다.** 이후 기능 개발이 그대로 이어붙는 **실제 스택 위의 골격**으로 만든다.

| | 만드는 것 | 만들지 않는 것 |
| --- | --- | --- |
| 스택 | **Next.js App Router · Tailwind · shadcn/ui** — 확정 스택 그대로 | 별도 프로토타이핑 도구 |
| 데이터 | **목 픽스처** — 화면이 요구하는 모양대로 | DB · Prisma 스키마 |
| 라우팅 | route group `(guardian)` · `(child)` **실제 구조** | 임시 페이지 |
| 컴포넌트 | `src/modules/*` 경계를 지킨 **실제 컴포넌트** | 일회용 마크업 |

> **이렇게 하는 이유** — 나중에 목을 실제 데이터 접근으로 바꾸는 것이 전부여야 한다.
> 별도 도구로 그리면 옮기는 작업이 통째로 낭비가 된다.

## 5. 🔴 신규 태스크 — MCK-001 목 픽스처

**우리 태스크 리스트에 Mock 태스크가 없다.** 레퍼런스 사례에는 `MCK` Epic이 있었으나 우리는 서버 진입점을
경계로 분해해 목 계층을 따로 두지 않았다. **프로토타입에는 필수다.**

### 왜 화면 태스크에 흡수시키지 않는가

| 이유 | 내용 |
| --- | --- |
| **네 화면이 같은 목을 쓴다** | 각자 만들면 나무의 「실천 3회」와 숲의 「실천 집계」가 어긋난다 |
| **빈 상태가 목의 일부다** | 실천 0건 · 전월 데이터 없음 · 소비 없음 — **화면마다 만들면 빠뜨린다** |
| **이후 교체 지점이 된다** | 목을 한 곳에 두어야 실제 데이터 접근으로 바꿀 때 **바꿀 곳이 명확**하다 |

### 담아야 할 픽스처

```
정상   나무 4영역(씨앗·새싹·나무 혼합) · 숲 전월 델타 7항목 · 계획↔실제 지킴/넘김
       별 잔액 충분 · 승인 대기 3건
경계   정체 14일 경과(원인 복수) · 계획 업종 불일치 · 별 잔액 부족
빈     실천 0건 · 전월 데이터 없음 · 계획 카드 없는 결제
```

> **빈 상태 3종을 반드시 넣는다.** 이 제품에서 가장 먼저 확인해야 할 화면이다.

## 6. 의존성 우회 — 무엇을 목으로 대체하나

선별한 UI 태스크는 각각 **백엔드 선행 1건**을 갖는다. 프로토타입에서는 이를 **MCK-001로 대체**한다.

| UI 태스크 | 원래 선행 | 프로토타입에서 | 나중에 |
| :-: | :-: | --- | --- |
| GRW-003 | `GRW-002` 정체 판정 | 목: 정체 14일 경과 시나리오 | GRW-002 완료 시 교체 |
| GRW-005 | `GRW-004` 숲 스냅샷 | 목: 전월 델타 7항목 | GRW-004 완료 시 교체 |
| PLN-004 | `PLN-003` 두 갈래 회고 | 목: 지킴/넘김/업종 다름 3갈래 | PLN-003 완료 시 교체 |
| STR-003 | `STR-001` 별 원장 | 목: 잔액 · 다음 아이템까지 남은 별 | STR-001 완료 시 교체 |

**목으로 대체하지 않는 것** — `INF-002` 의 선행 `INF-001` · `UX-001` 은 **실제로 먼저 해야 한다.**
앱과 토큰이 없으면 화면을 만들 수 없다.

## 8. 이 프로토타입이 검증하는 것

SRS §9.4의 실험 중 **화면만으로 돌릴 수 있는 것**이다. 프로토타입의 진짜 목적은 여기 있다.

| 실험 | 무엇을 보나 | 통과선 | 필요한 화면 |
| :-: | --- | :-: | --- |
| **E1** | 나무를 **5초만** 보여주고 덮은 뒤 행동 변화를 1문장으로 회상 | ≥ 6/8 | GRW-003 · GRW-005 |
| **E2** | *"나무가 자랐다는 건 뭘 했다는 뜻인가"* — 개입 없이 **「실천」에 도달** | ≥ 6/8 | GRW-003 |
| **E5** | 정체 원인을 보여주고 **오귀인 · 앱 불신 발화**를 코딩 | 각 ≤ 2/8 | GRW-003 (정체 시나리오) |
| **E6** | 보호자가 **금융 집중을 원하는가** 반증 인터뷰 | (a) ≥ 5/8 | 전 화면 |
| **E8** | 회고 화면 **체류 시간**과 두 갈래 구별 | p50 ≥ 3초 | PLN-004 |
| E4 *(부분)* | 첫 실천 인정률 — **별 지급 로직이 필요**해 목으로는 한계 | ≥ 60% | 본 개발 이후 |

**돌릴 수 없는 것** — `E3`(계획 카드 작성률) · `E7`(업종 매칭 정확도)은 **실제 결제 계측**이 필요하다.
둘은 선결 과제 ①②이며 프로토타입 밖이다.

> 즉 이 프로토타입은 **선결 과제 ④를 수행하고 ⑤ 인터뷰 8슬롯의 입력을 만든다.**

## 9. ⚠️ 하네스 원칙과의 충돌 — 의도적 예외

`CLAUDE.md` 와 스킬 `400-task-execution-workflow` 는 이렇게 못 박고 있다.

> **선행이 안 끝났으면 시작하지 않는다.**

**프로토타입은 이 원칙의 예외다.** 백엔드 선행 4건을 목으로 대체하고 UI를 먼저 만든다.
예외를 두는 이유와 조건을 명시한다.

| 항목 | 내용 |
| --- | --- |
| **왜 예외인가** | SRS §9.4 선결 과제 ④가 프로토타입이고, 그 결과가 ⑤ 인터뷰의 입력이다. **계획이 요구하는 순서다** |
| **어디까지 예외인가** | **UI 태스크 4건의 백엔드 선행만.** `INF-001` · `UX-001` 같은 실제 선행은 지킨다 |
| **무엇을 하지 않는가** | 목을 실제 데이터인 것처럼 두지 않는다. **`MCK-001` 한 곳에 모아** 교체 지점을 명확히 한다 |
| **언제 끝나는가** | 각 백엔드 태스크가 완료되면 **해당 화면의 목을 즉시 교체**한다. 목이 남아 있는 화면을 완료로 표시하지 않는다 |

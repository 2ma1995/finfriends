```
② 보호자 세션이 죽어도       OK          ← 부모 재로그인 불필요
③ 보호자가 동의를 철회하면   CONSENT_REQUIRED  ← 토큰이 살아 있어도 막힌다
④ 보호자가 기기를 해제하면   REVOKED
```

| 규칙 | 어떻게 |
| --- | --- |
| 🔴 별은 **승인에서만** 생긴다 | 「했어요」(`markDone`)는 `doneAt` 만 찍는다. `grantStar` 는 `approveMission` 안에만 있다. 아이 쪽 액션에서 원장을 건드리지 않는다 — 건드리면 아이가 별을 무한히 만든다 |
| 🔴 중복 지급 0건 | 멱등키가 `mission:<id>` **하나**다. 두 번 눌러도 `P2002` 로 막힌다 (REQ-NF-006) |
| 🔴 소급이 다음 주기를 부풀리지 않는다 | `cycleId` 는 **「했어요」 시점**에 박힌다. 승인은 이 값을 고치지 않는다 (ACE-6.2) |
| 🔴 「승인 대기」 ≠ 「미실천」 | 아이 화면이 세 구역으로 갈린다 — 오늘 할 수 있는 것 / 기다리는 중 / 지난 미션. 거절은 사유를 그대로 보여준다 (AC-6.2) |
| 🔴 결합 조회 차단 유지 | `missions.child_id` 는 `identity` 로 **FK 를 걸지 않았다**. `activity` 역할로는 아이 이름을 못 읽는다 (REQ-NF-009 · S3) |

**FK 를 안 건 대가** — 아이 행을 다시 만들면 미션이 **고아**로 남는다. 실제로 공유 개발 DB 에서
한 번 발생했다. 개발용으로 `app/prisma/seed-missions.mjs` 를 뒀다 — 아무것도 지우지 않고
현재 아이에게 미션만 다시 깐다. **운영에서는 아이 삭제 시 `activity` 정리 작업이 따로 필요하다 (미구현).**

**검증** — 실제 DB 대상 한 바퀴 전건 통과.

```
① 미실천 → ② 「했어요」: 잔액 그대로 (별 안 붙음)
③ 승인 1회 +2 · 2회째 P2002 거부 → 순증가 = 보상 (중복 0건)
④ 대기 중 되돌리기 성공  ⑤ 승인된 것 되돌리기 0건 (막힌다)
```

🔴 **아직 안 한 것** — 부모의 **미션 만들기** 화면이 없다. 지금은 시드로만 생긴다.

**설계에서 지킨 것**

여기가 그 자리다.

**검증** — 실제 DB 대상 전건 통과.


🔴 **아직 안 한 것** — 읽어 주기(음성)가 없다. 저학년은 글을 못 읽을 수 있다.
이모지와 짧은 문장으로 버티고 있지만 **접근성 요건으로 다시 봐야 한다.**

## D14 🔴 방·상점이 브라우저 localStorage 를 지갑처럼 쓰고 있었다

| 항목 | 내용 |
| --- | --- |
| 실제 | 별 잔액·보유 아이템·방 배치가 **브라우저**에 있었다 (`proto-store.ts` · `ff-proto-room-layout`) |
| 결과 | `activity.child_items` · `activity.child_room` 신설 (`20260831000010_child_items`) |

**왜 심각한가** — 기본값이 `별 40개 · 아이템 여러 개 보유`였다. 그래서 **오늘 가입한 아이가
이미 꾸며진 남의 방을 자기 방으로 봤다.** 게다가 별 원장에는 `WARDROBE_SPEND` 차감이 남는데
**무엇을 샀는지가 어디에도 없어** 원장과 화면이 서로를 몰랐다 — 정합성 검증이 불가능하다(REQ-NF-006).
기기를 바꾸거나 사생활 보호 모드로 열면 꾸민 방이 통째로 사라지기도 했다.

**설계에서 지킨 것**

| 규칙 | 어떻게 |
| --- | --- |
| 🔴 별을 두 군데서 세지 않는다 | 잔액은 언제나 **원장의 합**이다. 상점이 따로 들지 않는다 |
| 🔴 별과 물건이 한 거래다 | `buyItem` 이 차감과 보유 등록을 함께 한다. 나뉘면 **별만 나가고 물건이 안 오는 아이**가 생긴다 |
| 🔴 두 번 눌러도 한 번 | 멱등키 `buy:<child>:<item>` (REQ-NF-003 오프라인 큐) |
| 🔴 빚을 지지 않는다 | 잔액 검사는 `grantStar` 안에서 원장 합을 보고 한다 |
| 🔴 안 가진 물건은 방에 못 둔다 | `saveLayout` 이 요청의 id 를 보유와 대조해 거른다 |
| 잠긴 것은 회색 | 숨기지 않는다 — 아이가 목표를 세울 수 있어야 한다 (사용자 결정) |

**카탈로그는 코드에 남긴다** — `contracts/items.ts`. GLB·썸네일 정의는 **에셋이지 회원 데이터가
아니다.** DB 는 「누가 무엇을 가졌는가」만 안다.

**`layout` 은 JSON 한 칸이다** — 방 안 좌표를 컬럼으로 펼치면 이름만 보고 **위치정보로
오해될 수 있다.** 규제 스캔 오탐을 피하려고 묶어 뒀다. 화면 좌표이지 위치 정보가 아니다.

**검증** — 실제 DB 대상 전건 통과.

```
① 새 아이 별 0 · 가진 것 0 (빈 방)   ② 별 0에서 사기 → 거부 (빚 안 짐)
④ 고양이(20) 구매 → 잔액 5           ⑤ 같은 것 재구매 → 두 번 안 나감
⑥ 토끼(25) → 모자라서 거부           ⑦ 안 가진 dog 를 방에 심기 → 걸러짐
```

🔴 **아직 안 한 것** — 아이템을 **되팔거나 환불하는 길이 없다.** 잘못 산 아이는 되돌릴 수 없다.

## D15 🔴 「배우기」에 배울 것이 없었다

| 항목 | 내용 |

| 실제 | 영역을 누르면 **곧장 퀴즈**로 갔다. 학습 콘텐츠가 한 편도 없었다 |

**고친 것**

| | |
| --- | --- |
| 학습 9편 (`contracts/lessons.ts`) | 벌기·잘 쓰기·모으기 각 3편. 한 편은 화면 하나를 넘지 않는다 |

| 흐름 | 배우기 → 영역 → 편 읽기 → (마지막 편) → 퀴즈. 예전엔 배우기 → 퀴즈였다 |
| 🔴 다시 읽어도 진도가 안 오른다 | 개수 대신 **읽은 편의 id 목록**을 담는다 (`completed_lessons`) |
| 🔴 읽기로는 별을 주지 않는다 | 주면 아이는 넘기기만 한다. SRS 트리거에도 없다 |
| 🔴 문항 수를 지어내지 않는다 | 총 수는 문항 은행이 센다. 틀린 문제는 다시 풀 수 있다 |

**콘텐츠는 코드에 남긴다** — 아이템 카탈로그와 같은 이유다. 글이지 회원 데이터가 아니다.
DB 는 **누가 무엇을 읽었는가**만 안다. `DAT-003` 이 콘텐츠를 DB 로 옮기면 모듈만 고치면 된다.

**검증** — 실제 DB 대상 전건 통과.

```
① 새 아이 진도 0행 (가짜 진도 없음)   ③ 같은 편 다시 읽기 → 안 오름
⑥ 같은 문항 다시 맞히기 → P2002 거부 · 별 그대로 · 퀴즈 수 안 부풂
```

🔴 **아직 안 한 것** — 읽어 주기(음성)가 없다. D13 과 같은 문제다.
「불리기(GROW)」는 여전히 잠겨 있다 — 실천 경로가 미개통이다.

## D16 🟠 「불리기」를 명세보다 더 잠갔다 · 별을 행동에 붙인다

### ① 불리기 — 학습까지 잠갔던 것

| 항목 | 내용 |
| --- | --- |
| SRS | **「불리기」는 학습만 열리고 실천은 닫혀 있다** (`isPracticeOpen(topic)` · AC-2.4) |
| 실제 | 영역 **전체**를 잠갔다. 아이가 **배울 기회조차 없었다** |
| 결과 | 학습·퀴즈를 열고 **실천만** 닫았다 |

**실천이 닫힌 이유는 진짜다** — 불리기의 실천은 **적금 가입~만기**다(GRW-001: 다른 영역은 매달
초기화, 불리기만 적금 시작~만기). 실제 금융상품과 카드 배송이 있어야 인정된다. 여기가 경계선이다.
**「곧 열려요」는 이제 실천에만 붙는다.**

🔴 실천 신청은 **서버에서도 막는다**(`claimPractice` 첫 검사). 화면만 감추면 요청은 그대로 통한다.

🔴 **금융상품을 권하지 않는다.** 불리기 3편은 이자의 원리 · 물가와 돈의 가치 ·
「늘 수도 줄 수도 있다」만 말한다. 특정 상품·투자처를 권하는 순간 교육이 아니라 권유가 된다.

### ② 별을 지식이 아니라 행동에 붙인다

| 항목 | 내용 |
| --- | --- |
| 이전 | 퀴즈를 틀리면 끝. 「다시 풀기」로 정답을 맞힐 때까지 반복 |
| 지금 | 틀리면 **설명만 보고 넘어간다.** 대신 배운 걸 하면 「해봤어요」로 별을 받는다 |

**왜** — 틀린 문제를 다시 풀게 하는 건 **정답 맞히기 연습**일 뿐이다. 이 제품의 규칙은
「배우고 → 해본다」이고, 별은 **행동**에 붙어야 한다.

| 규칙 | 어떻게 |
| --- | --- |
| 🔴 여기서 별을 주지 않는다 | 보호자 승인 → `MISSION_APPROVED`. 아이가 자기 실천을 스스로 인정하면 실천 인정이 무의미해진다 |
| 🔴 한 편당 한 장 | `missions(child_id, source_id)` 부분 유니크. 두 번 눌러도 승인 대기가 두 줄로 안 는다 |
| 🔴 거절돼도 다시 신청 | 같은 줄을 되살린다. 한 번 거절로 영영 막히면 다시 해볼 이유가 없다 |
| 🔴 안 읽은 편은 안 보인다 | 배우기를 건너뛰고 별만 받아 가는 길이 된다 |
| 부모 화면이 출처를 가른다 | 「📚 아이가 배우고 스스로 함」. 같아 보이면 보호자는 자기가 시킨 줄 안다 |

### ③ 콘텐츠를 공개 자료 기반으로 다시 썼다

학습 12편 · 문항 12개. 근거는 `resources/` 의 두 자료다 — 금융감독원 「초등 3·4학년
금융생활 익힘책」, 「초등학교 슬기로운 생활금융」. **원문을 옮기지 않았다.** 개념과
**오개념**만 가져와 우리 문장으로 썼다.

오답 선택지가 특히 달라졌다. 예전엔 지어낸 뻔한 오답이었는데, 이제 자료가 실제로
교정하려는 오해를 쓴다 — 「돈 버는 방법은 직업뿐」 · 「먼저 쓰고 남으면 저축」 ·
「돈이 많아서 고민이 생긴다」 · 「투자는 저축보다 항상 많이 번다」.

### ④ 세 축을 4영역에 붙였다 — 5번째 영역을 만들지 않았다

자료가 크게 다루는 **신용 · 개인정보 · 위험** 축은 각각 제 자리가 있었다.

| 축 | 어디로 | 왜 |
| --- | --- | --- |
| 신용카드 | **잘 쓰기** | 카드는 **지불 수단**이다. 「공짜로 사는 것」이 아니라 「나중에 내가 내는 것」 |
| 이자의 양면 | **불리기** | 맡기면 받고 빌리면 낸다. 「빌린 돈으로 불리지 않는다」의 근거 |
| 개인정보 · 수상한 문자 | **모으기** | **모은 돈을 지키는 일**이다. 통장 비밀번호도 이미 여기 있다 |
| 위험 대비 | **모으기** | 자료도 저축하는 이유 중 하나로 든다. 별도 편 대신 `save-1` 에 한 줄로 넣었다 |

**왜 5번째 영역을 안 만들었나** — 영역을 늘리면 아이가 외워야 할 이름만 늘고,
**나무 승급 규칙(§6.2.1)을 다시 짜야 한다.** 4영역은 SRS 가 고정한 구조다.

이로써 **영역당 학습 4편 · 문항 4개**로 고르게 맞췄다 (16편 · 16문항).

🔴 **아직 안 한 것** — 보험 자체(보험료 ↔ 보험금 ↔ 약관)는 저학년에게 이르다고 보고
「대비해서 모은다」는 개념만 심었다. 고학년 확장 때 다시 볼 자리다.

## D17 🔴 아이 화면의 쓰기 경로가 끊겨 있었다 — 위시리스트 · 계획↔실제

두 화면이 **읽기 전용**이었다. 학습은 「여기 적어 두세요」라고 안내하는데 적을 데가 없었다.

### ① 위시리스트 (PRC-004)

| 이전 | 지금 |
| --- | --- |
| 추가·저금·삭제·순위 액션 **0개** | 목표 추가 · 모은 돈 넣기 · 지우기 · 순위 올리기(월 1회) |

| 규칙 | 어떻게 |
| --- | --- |
| 🔴 재도달 중복 지급 0건 (REQ-TEC-011) | `reachedSteps` 는 줄어들지 않는다. 진행률이 내려갔다 올라도 두 번 안 준다 |
| 🔴 WPA 분자 산입 (PRC-004) | `PracticeCredit` 을 남긴다 — 퀴즈와 다른 점이다 |
| 자기 신고 한계 | 목표 5개 · 1,000~1,000,000원 · 1회 100,000원 |

**왜 한계가 필요한가** — 모은 돈은 **아이가 스스로 적는다**(용돈기입장과 같다).
한계가 없으면 100원짜리 목표를 계속 만들어 별을 무한히 받고, **실천 지표가 통째로 거짓이 된다.**

### ② 계획 ↔ 실제 (PLN-002 · PLN-003)

고리가 이렇게 끊겨 있었다.

```
계획 적기 ✅ → 계획 목록 ❌ → 실제로 쓴 돈 적기 ❌ → 회고 ⚠️(시드만)
```

계획은 `activity.plan_cards` 에 저장되는데 **아이가 다시 볼 화면이 없었고**,
`spending_records` 를 만드는 코드가 **어디에도 없었다.** 회고는 시드가 넣은 2건으로만 열렸다.

`/child/plan` 목록과 「얼마 썼는지 적기」를 만들어 닫았다.

| 규칙 | 어떻게 |
| --- | --- |
| 🔴 ⭐ 판정은 **금액 단독** (ADR-008) | 업종이 달라도 금액을 지켰으면 준다. 섞으면 「업종이 달라서 별을 못 받았다」로 오해한다 |
| 🔴 넘겨도 **차감하지 않는다** (P-03) | 미지급일 뿐이다. 화면도 「넘겨도 괜찮아요」라고 말한다 |
| 🔴 계획 하나에 실제 하나 | 다시 적어 별을 또 받을 수 없다. 멱등키도 계획 id 다 |
| 🔴 지킴은 **실천**이다 | `PracticeCredit` 을 남긴다 (성장 나무 「계획 지키기」) |

**원래 설계는 실제 지출이 카드 연동(`DAT-004`)에서 온다.** 그게 붙기 전까지 손으로 적는다.

### ③ 함께 발견한 것 — `PracticeCredit` 을 아무도 안 쓰고 있었다

`modules/growth` 는 `practiceCredit` 을 읽는데 **쓰는 코드가 하나도 없었다.**
즉 **부모의 성장 나무가 영원히 0이었다.** 이번에 위시리스트 도달과 계획 지킴에서 남기기 시작했다.

🔴 **아직 안 한 것** — **미션 승인**(`approveMission`)이 아직 `PracticeCredit` 을 남기지 않는다.
미션이 실천의 주된 경로이므로 여기가 제일 크다. 승급 판정(GRW-001)도 여전히 없다.

**검증** — 실제 DB 대상 전건 통과.

```
위시리스트  8,000(33%)→⭐1 · 17,000(70%)→⭐2 · 24,000(100%)→⭐3
            0으로 내렸다 다시 100% → 새 단계 없음 (중복 0건)
계획↔실제   5,000 계획에 4,500 씀 → 지킴 ⭐1 · 같은 계획 재시도 → 거부
            2,000 계획에 3,500 씀 → 넘김, 별 그대로 (차감 없음)
            도서 계획인데 간식 8,000 → 지킴 ⭐ (업종 무관 · ADR-008)
```

## D18 🔴 용돈 장부 — 아이가 아무 숫자나 적던 것을 실제 잔액에서 빼게 한다

| 이전 | 지금 |
| --- | --- |
| 위시리스트 「모은 돈」을 아이가 **아무 숫자나** 적었다 | 보호자가 준 **용돈 잔액에서 떼어 온다** |
| 계획 실제 지출도 장부와 무관했다 | 쓴 만큼 용돈에서 빠진다 |

**결과** — `activity.allowance_ledger` 신설 (`20260831000013_allowance`) · 보호자 화면 `/parent/allowance`.

### 🔴 규제선 — 앱은 돈을 보관하지 않는다

사용자 요청은 「부모가 충전해준 카드에서 빠져나가게」였다. **충전식 선불카드는 만들지 않았다.**
앱이 실제로 가치를 보관하면 **선불전자지급수단**이 되어 전자금융업 등록 대상이고, 아동 명의
문제까지 겹친다.

대신 **장부**로 만들었다 — 실제 돈은 현금·보호자 카드로 앱 **밖에서** 오가고, 앱에는
「얼마 줬고 얼마 남았나」만 적힌다. 아이가 겪는 경험은 같다.
보호자 화면 **첫 카드가 이 사실을 그대로 말한다** — 오해를 만들면 안 된다.

### 🔴 별과 절대 섞이지 않는다 (P-21 · REQ-NF-010 · S4)

| 규칙 | 어떻게 |
| --- | --- |
| 전환 함수를 두지 않는다 | `modules/allowance` 는 `modules/star-ledger` 를 **import 하지 않는다.** 그 사실이 파일 첫 줄에서 보인다 |
| 표를 나눈다 | `star_ledger` ↔ `allowance_ledger`. 별로 용돈을 못 사고, 용돈으로 별을 못 산다 |
| 금지 심볼 회피 | `cash` · `withdraw` · `convert` 를 쓰지 않는다 (REQ-TEC-008 정적 검사) |

별이 나가는 곳은 여전히 **앱 내 재화(옷장·방 아이템)뿐**이다.

### 지킨 것

| 규칙 | 어떻게 |
| --- | --- |
| 🔴 잔액을 저장하지 않는다 | 원장의 합이 잔액이다 — 별 원장과 같은 규율 (REQ-NF-006) |
| 🔴 0 밑으로 안 내려간다 | 없는 돈을 쓴 것으로 적으면 장부가 현실과 어긋나고, 그때부터 화면이 무의미해진다 |
| 🔴 중복은 정상 경로 | 멱등키로 막는다. 연타·오프라인 재전송이 두 번 빠지지 않는다 (REQ-NF-003) |
| 🔴 목표를 지우면 되돌린다 | 안 되돌리면 **아이 돈이 앱 안에서 사라진다.** 이미 받은 별은 되돌리지 않는다 — 그때 실제로 모았던 것은 사실이다 |

**부수 효과 — 별 farming 이 막혔다.** 예전엔 100원짜리 목표를 만들고 아무 금액이나 적어
⭐ 3개를 받을 수 있었다. 이제 **없는 돈은 못 넣는다.** 한계값으로 막던 것을 구조로 막는다.

**검증** — 실제 DB 대상 전건 통과.

```
② 20,000 받음  ③ 8,000 떼어 둠 → 12,000  ④ 같은 조작 재전송 → 두 번 안 빠짐
⑤ 50,000 시도 → 거부 (없는 돈 못 씀)     ⑥ 목표 삭제 → 20,000 복원 (돈이 안 사라짐)
⑦ 4,500 씀 → 15,500 · 별은 0 그대로 (두 원장이 안 섞인다)
```

### ⑤ 정정 — 줄을 고치지 않고 **반대 줄을 적는다** (추가 구현)

원장에서 줄을 수정·삭제하면 **「합이 잔액」이 깨지고 왜 이렇게 됐는지 아무도 못 본다.**
회계와 같이 상쇄하는 줄을 새로 적는다.

| 규칙 | 어떻게 |
| --- | --- |
| 🔴 보호자가 적은 줄만 되돌린다 | `TOPUP` · `ADJUST` 만. 아이 기록을 보호자가 임의로 지우면 아이는 자기 장부를 못 믿는다 |
| 🔴 되돌릴 수 있는 만큼만 | 20,000원을 잘못 줬는데 아이가 15,000원을 이미 넣었으면 **5,000원만** 돌아온다 |
| 🔴 못 되돌린 만큼을 그대로 말한다 | 조용히 넘기면 보호자는 다 취소된 줄 안다 |
| 🔴 한 줄당 한 번 | 멱등키 `adjust:<줄id>` |
| 아이도 본다 | 「부모님이 고쳤어요 — 사유」. 잔액이 말없이 줄면 아이는 앱이 고장 난 줄 안다 |

**아이 용돈 기입장 `/child/allowance` 를 함께 만들었다.** 두 공개 자료가 **가장 강조하는
실천이 용돈기입장 쓰기**다 — 날짜·내용·들어온 돈·나간 돈·남은 돈 다섯 칸을 그대로 옮겼다.

## D19 🟠 카드 연동 — 예시 데이터로 흐름을 먼저 세운다

`activity.card_transactions` 신설 (`20260831000014_card_txn`) · `prisma/seed-card.mjs`.

**아직 실제 연동이 아니다.** `source = MOCK` 인 줄만 들어오고, 화면이 **「예시 · 카드 연동 전」**
이라고 밝힌다. 실제 연동(`DAT-004`)은 제휴 카드사가 발급하고 **자금은 카드사가 보관**한다 —
앱은 내역만 받는다. 그래야 D18 의 선(앱은 돈을 보관하지 않는다)이 유지된다.

### 🔴 카드가 손입력을 대체하지 않는다

두 공개 자료가 **가장 강조하는 실천이 용돈기입장 쓰기**다. 카드가 자동으로 적어 주면
**그 학습이 사라진다.** 편해지는 건 부모이지 아이가 아니다.

그래서 카드 내역은 **대조용**이다.

| | |
| --- | --- |
| 계획 화면 | 카드 내역을 눌러 금액을 채운다. **채운 뒤 고칠 수 있다** |
| 회고 화면 | 「적은 것보다 1,500원 더 썼네요」 — **자동으로 고쳐 주지 않는다** |

**차이를 마주하는 것이 학습 장면이다.** 시드가 카드 금액을 계획과 **일부러 어긋나게** 넣는다 —
딱 맞으면 대조할 게 없다.

🔴 한 거래는 **한 번만 쓰인다** (부분 유니크 인덱스). 같은 거래로 두 계획을 맞춰 별을
두 번 받을 수 없다.

**검증** — 실제 DB 대상 전건 통과.

```
정정  ② 그대로 되돌리기 20,000 → 잔액 0
      ④ 아이가 15,000 쓴 뒤 되돌리기 → 5,000만 · 못 되돌린 15,000 그대로 알림
      ⑤ 또 되돌리기 → 거부   ⑥ 아이 기록 고치기 → 거부   ⑦ 지운 줄 0
카드  ⑨ 카드 4,500 ↔ 아이가 적은 3,000 → 차이 1,500 (회고가 보여준다)
      ⑩ 같은 거래 재사용 → 0건
```

🔴 **아직 안 한 것** — 실제 연동은 **개발이 아니라 제휴 일정**이다(카드사 계약·심사).
마이데이터 방식은 본인신용정보관리업 허가가 필요하고 아동 계좌는 더 까다로워 후순위다.
영수증 OCR 은 **넣지 않는다** — AI 제약 위반이고, 금액 오인식이 곧 장부 오류가 된다.

### D20-b 승급 엔진 자리 — 단계를 읽는 대신 **읽는 시점에 계산한다**

아이 화면에 생긴다. 시연 데이터이므로 버렸다.

### D22-b — 같은 증상이 한 번 더 났다. 이번엔 **「잔액」이 두 개념**이었다

컬럼을 없앤 뒤에도 부모 화면과 아이 화면의 금액이 갈렸다. 원인이 다르다.

```
TOPUP          +20,000   9월 용돈
WISH_SET_ASIDE  -8,000   물감 세트에 넣었어요
PLAN_SPEND      -1,500   편의점에서 썼어요
```

원장 합은 **10,500원**인데 아이가 가진 돈은 **18,500원**이다 —
**목표에 떼어 둔 8,000원은 쓴 게 아니라 묶인 것**이다.
실제 통장의 「출금가능금액」과 「잔액」이 다른 것과 같은 구분이다.

**부모 화면이 더 나빴다.** 그 8,000원을 **이자율을 설정했을 때만** 보여줬다 —
이자 카드 안에 「모은 돈」으로 들어가 있어서, 이자율을 안 정하면 화면 어디에도 없었다.
**이자는 부가 기능인데 그 안에 원금을 둔 것**이다. 부가 기능을 안 켜면 원금이 사라진다.

| 고친 것 | |
| --- | --- |
| 세는 곳 | `modules/allowance.getWalletTotals` **하나뿐** — `{ free, setAside, total }`. `modules/bank` 가 따로 하던 `wishlist` 집계는 지웠다. **각자 세면 또 갈린다** |
| 화면 | 세 갈래를 **이자 카드 밖**으로. 「가진 돈 18,500 / 쓸 수 있는 돈 10,500 / 목표에 넣어 둔 돈 8,000」 + 「쓴 게 아니라 묶어 둔 돈이에요」 |
| 기록 | `MOVED_CODES` 로 「목표로 옮김」을 「나감」과 구별한다 — 같아 보이면 부모도 쓴 걸로 읽는다 |
| 되돌리기 문구 | 「남은 용돈이 없어서」 → 「목표에 넣어 둔 돈은 **지금** 되돌릴 수 없어요」. 아이가 목표를 지우면(`WISH_RELEASE`) 다시 되돌릴 수 있게 되므로 「지금은」이 정확하다 |

`reverseEntry` 가 `free` 로 한도를 잡는 것은 **그대로 둔다** — 목표에 묶인 돈까지 회수하면
부모 조작으로 아이 목표가 깨진다.

**교훈** — 컬럼을 없앤다고 끝이 아니었다. **같은 값을 두 곳에서 세면 저장 위치가 하나여도 갈린다.**

**할 일** — `tools/tasks_data.py` 의 「아이 통장」 화면 설명에서 잔액 출처를 원장으로 적고,
**잔액이 세 갈래**라는 것을 함께 적는다.
`D18`(용돈 장부)과 `D21`(아이 통장)이 같은 원장을 쓴다는 것을 SRS 데이터 모델에 남긴다.

| 구현 | `/child/enter?t=<토큰>` — 보호자가 만든 링크를 아이 기기에서 한 번 열면 그 기기가 아이에게 묶인다 |
| 어긋남 | 주소에 실리는 `t` 가 **일회용 초대 코드가 아니라 기기 토큰 그 자체**다. 쿠키에 그대로 심겨 180일간 모든 접근 판정에 쓰인다 |
| 발견 | 아이 화면 세션이 만들면서 스스로 적어 뒀고(`route.ts` 주석), 부모 쪽에서 대장에 올렸다 (2026-09-01) |
| 상태 | **개발·시연용으로 의도한 것.** 운영 전에 반드시 바꾼다 |

**왜 위험한가** — 주소는 여러 곳에 남는다. 브라우저 방문 기록 · 서버와 프록시 접근 로그 ·
바깥으로 나가는 링크의 `Referer` 헤더 · 메신저 링크 미리보기 · 화면 공유.
그 문자열 하나면 **누구든 그 아이의 화면에 들어간다.** 보호자가 알아차리고
기기를 해제할 때까지 유효하다.

**이미 지키고 있는 것** (없는 위험을 부풀리지 않는다)

- 토큰은 `randomBytes(32)` 이고 DB 에는 **sha256 해시만** 있다 — 유출돼도 DB 쪽에서 새지 않는다
- 심을 때 **`httpOnly`** 다. 화면 스크립트가 읽지 못한다
- 리다이렉트에서 **쿼리를 지운다**(`url.search = ""`) — 주소창에 남지 않는다
- **먼저 확인하고 심는다.** 틀린 토큰이 조용히 남아 잠금 화면만 보는 일이 없다
- 마이페이지 「기기 해제」로 **즉시 무효화**된다 (`revokeDevice`)

**그래도 남는 것** — 위 다섯은 전부 *심은 뒤* 를 지킨다. 링크가 **전달되는 동안**은
그대로 노출된다. 그리고 노출되는 값이 세션 토큰이 아니라 **자격증명 본체**다.

**고치는 방향** — 주소에 싣는 것을 **한 번 쓰면 죽는 짧은 초대 코드**로 바꾸고,
`/child/enter` 가 그 코드를 **새 기기 토큰으로 교환**한다. 코드는 첫 사용에서 소멸하고
유효 기간은 분 단위다. 그러면 링크가 새도 이미 쓰인 코드는 쓸모가 없다.

**🔴 아동 독립 로그인은 아니다** — 링크를 만드는 주체는 보호자이고 아이는 아무것도
입력하지 않는다. `S5`(아동 독립 로그인 0건)를 어기지 않는다. 어긋난 것은
**자격증명 전달 방법**이지 인증 모델이 아니다.

**할 일** — `tools/tasks_data.py` 의 `CON-004`(기기 등록)에 초대 코드 교환을 추가한다.
`SRS §6.1` 진입점 표에 `/child/enter` 를 올린다 — 지금 표에 없는 진입점이다.
운영 배포 전 필수이며, 시연까지는 지금 형태로 둔다.

## D25 🟠 「불리기」 실천을 여는 길 — 우리 집 적금

| 항목 | 내용 |
| --- | --- |
| SRS | `SAVINGS_JOINED`(⭐1) · `SAVINGS_DONE`(**⭐10**) 이 정의돼 있다 |
| 실제 | **쓰는 곳이 없었다.** 그래서 불리기 나무가 자랄 방법이 아예 없었다 |
| 결과 | `activity.savings_plans` 신설 (`20260901000019_savings`) · 아이 통장 안에 신청 칸 |

**🔴 규제선 — 외부 가입을 중개하지 않는다** (P-20 · REQ-NF-012).

`modules/savings` 에 **외부 링크도, 외부 API 호출도 없다.** 여기 있는 것은 **부모와 아이의
약속**이고 이자는 **부모가 자기 돈으로** 준다. 금융상품이 아니다. 화면도 그렇게 말한다 —
「은행 적금이 아니라 부모님과 하는 약속이에요」. 아이가 실제 상품으로 오해하면 안 된다.

**흐름**

```
아이가 신청 (무엇을 위해 · 얼마 · 몇 달)
  → 🔴 여기서 돈이 묶이지 않는다. 거절당하면 아이 돈이 잠깐 사라진다
보호자가 받아들임 → 용돈에서 묶임 · ⭐1 (SAVINGS_JOINED)
  ├─ 만기까지 지킴 → 원금 + 이자 · ⭐10 (SAVINGS_DONE)
  └─ 중간에 깸    → 원금만 · 이자 없음 · 별 없음
```

**설계에서 지킨 것**

| 규칙 | 어떻게 |
| --- | --- |
| 🔴 아이가 시작하지 않는다 | 신청만 한다. 아이가 시작까지 하면 **부모 돈으로 주는 이자를 아이가 정하는** 셈이다 |
| 🔴 이자율을 **신청 시점에 박는다** | 뒤에 부모가 바꿔도 이 약속은 그대로다. 약속한 뒤 조건이 바뀌면 그건 약속이 아니다 |
| 🔴 한 번에 하나 | 부분 유니크 인덱스. 여러 개를 굴리면 아이가 무엇을 지키는지 모른다 |
| 🔴 만기 전 완료 불가 | 날짜를 안 보면 아이가 바로 눌러 ⭐10을 받는다 |
| 🔴 **깨는 것을 막지 않는다** | 아이 돈이다. 대신 **누르기 전에 대가를 말한다** — 「지금 깨면 이자를 못 받아요」 |
| 묶인 돈도 「가진 돈」이다 | `getWalletTotals` 에 `locked` 를 더했다. 안 그러면 또 「돈이 사라졌다」가 된다 |

**중도 해지가 이 기능의 학습 가치다.** 두 공개 자료가 「만기 전에 찾으면 약속한 이자를
다 못 받는다」를 가르친다. 막지 않고 **겪게 한다** — 그게 배우는 방법이다.

**검증** — 실제 DB 대상 전건 통과.

```
② 신청만으로는 안 묶임   ③ 두 번째 신청 → P2002 거부
④ 승인 → 10,000 묶임 · ⭐1 · **가진 돈 20,000 그대로**
⑤ 만기 전 완료 → 거부    ⑥ 중간에 깸 → 원금만 · 이자·별 없음
⑦ 만기까지 지킴 → 이자 1,000원 · ⭐10
   깼을 때 ⭐1 vs 지켰을 때 ⭐11
```

### 🔴 보강 — 이자율 칸을 없애자 **새 집이 영영 신청을 못 하는 잠금**이 생겼다

통장의 이자율 설정 칸을 없앤 것은 맞다 — **같은 값을 두 곳에서 정하면 갈린다.**
보호자는 이미 승인 화면에서 건마다 이자율을 정하고, 이자율은 **신청하는 순간** 약속에
박히므로 통장에서 바꿔도 이미 올라온 신청은 안 바뀐다.

**그런데 아이 화면이 「이자율이 없으면 신청 폼을 감추고」 있었다.** 정하는 칸이 사라졌으니
새 집은 이렇게 갇힌다.

```
이자율 없음 → 신청 폼 안 열림 → 신청 없음 → 승인 없음 → 기본값 안 생김 → 이자율 없음
```

**두 곳을 함께 고쳐야 닫힌다.**

| | |
| --- | --- |
| `accept()` | 보호자가 정한 이자율을 **그 집 기본값으로도 남긴다.** 유일한 갱신 지점이다 |
| 아이 화면 | **막지 않는다.** 「이자는 부모님이 받아 주실 때 정해 주세요」로 열어 둔다 |

**검증** — 이자율이 한 번도 없는 집으로 시작.

```
① 우리 집 이자 (안 정함)   ② 신청 → 막히지 않음 · 신청서 0% · 아이가 바란 10%
③ 부모가 7% 로 승인 → 이 약속 7% · **우리 집 이자 7%**
④ 다음 신청 기본값 7% — 0% 로 돌아가지 않는다
```

**교훈은 앞과 같다** — 한쪽 화면에서 무언가를 없앨 때 **그 값을 읽는 다른 화면의 분기**를
함께 봐야 한다. 잔액에서 두 번, 이자율에서 한 번 같은 곳에서 미끄러졌다.

### 🔴 보강 — 「우리 집 적금」은 `REQ-FUNC-014` 가 아니다

`REQ-FUNC-014`(예적금 비교·선택)는 **Blocked (D2) · 법률 검토 통과 전 착수 불가**다.
가입 ⭐1 · 완주 ⭐10 과 「불리기 주기 = 적금 시작~만기」도 거기 적혀 있어서,
나중에 읽는 사람이 **막힌 요구사항을 만든 것으로 오해할 수 있다.** 다르다.

| | `REQ-FUNC-014` (막힘) | 우리 집 적금 (만듦) |
| --- | --- | --- |
| 무엇 | **외부 금융기관 예적금**을 비교하고 고르는 경험 | 부모와 아이의 **약속** |
| 이자 | 금융기관이 준다 | **부모가 자기 돈으로** 준다 |
| 걸리는 것 | P-20 가입 중개 — 법률 검토 대기 | 금융상품이 아니라 해당 없음 |
| 외부 연결 | 비교하려면 상품 정보가 필요하다 | **링크도 API 도 0건** |

트리거(`SAVINGS_JOINED` · `SAVINGS_DONE`)를 같이 쓰는 것은 **둘 다 「불리기 실천」이기
때문**이다. `REQ-FUNC-014` 가 열리면 그때 두 경로가 같은 트리거로 합류한다.

🔴 **법률 검토가 나오면 다시 봐야 한다.** 「부모가 주는 이자」도 검토 대상에 넣는 것이 안전하다.

### 🔴 보강 — 근거 없는 이자를 아이에게 보여주고 있었다

아이 통장이 **「갖고 싶은 것」에 넣어 둔 돈에 이자율을 곱해** 「지금이면 400원」을 보여줬다.
**줄 방법이 없었다.**

| 근거로 삼은 것 | 실제 |
| --- | --- |
| §10.1 **A3** 「보호자는 위시리스트 목표에 실제로 이자를 준다」 | **[검증 대기] 가정**이다 — 3개월 시점 종단 관찰(E10) 항목 |
| — | `REQ-FUNC-012`(위시리스트)는 **30·70·100% ⭐1 뿐**이고 이자가 없다 |

**가정 대장은 검증할 것을 적는 곳이지 만들 것을 적는 곳이 아니다.** 양쪽 화면이 같은
실수를 했다(부모 쪽은 `D28`).

**아이에게는 더 나쁘다** — 기다리는 숫자를 만들어 놓고 안 주는 것이기 때문이다.
「우리 집 이자 5% · 저금하면 5%를 받아요 · **저금(예금·적금)에만 붙어요**」로 바꿨다.
무엇에 붙는지 안 적으면 아이는 모든 돈에 붙는 줄 안다.

### 🔴 보강 — 예금을 「적금」이라 부르고 있었다

**이름을 잘못 붙였다.** 처음 만든 것은 목돈을 한 번에 묶는 **예금**인데 「적금」이라고 불렀다.
사용자가 「그럼 매일 저금이 되는 거지?」라고 물어서 드러났다.

학습 `save-3` 이 둘을 구별해 가르친다 — **정기 적금**은 매달 조금씩, **정기 예금**은 큰돈 한 번에.
`save-2` 는 「하루 100원이면 한 달 3,000원」으로 **조금씩 자주**를 강조한다.
그래 놓고 앱은 목돈을 한 번에 넣게 했다. **배운 것과 하는 것이 달랐다.**

**둘 다 만들었다** (`20260901000021_savings_kind`).

| | 예금 `DEPOSIT` | 적금 `INSTALLMENT` |
| --- | --- | --- |
| 넣는 법 | 목돈 한 번 | **매주 아이가 직접** |
| 시작 조건 | 전액이 있어야 한다 | **첫 회만** 있으면 된다 |
| 만기 | 개월 수 | 회차(주) 또는 **다 넣으면 즉시** |

🔴 **자동 이체로 만들지 않았다.** 자동이면 아이가 아무것도 안 해도 되고, 그러면 **실천이 아니다.**
매주 넣는 행동 자체가 「조금씩 꾸준히」를 배우는 방법이다. 한 번 묶고 끝나면 3달 동안
아무 일도 일어나지 않는다.

| 규칙 | 어떻게 |
| --- | --- |
| 🔴 한 주에 한 번만 | 안 그러면 하루에 열두 번 눌러 만기를 앞당긴다 |
| 🔴 이자는 **실제로 넣은 돈** 기준 | 약속만 하고 안 넣었는데 총액에 이자를 주면 안 된다 |
| 🔴 다 넣으면 날짜 전이라도 끝 | 12주치를 다 넣었는데 날짜만 기다리게 하면 아이는 왜 기다리는지 모른다 |
| 건너뛰어도 회차는 남는다 | 용돈이 모자란 주가 있다. 회차가 사라지면 벌이 된다 |
| 묶인 돈도 **넣은 만큼**만 | 약속 총액을 세면 아직 안 낸 돈까지 「가진 돈」에 잡힌다 |

**검증** — 한 주 1,000원 × 12주 적금.

```
② 신청에 12,000원이 필요한가 → 아니다. 첫 회 1,000원만
③ 승인 → 묶인 돈 1,000원 (첫 회만)     ④ 이번 주 재납입 → 거부
⑤ 12/12회 · 모은 돈 12,000            ⑥ 다 넣음 → 날짜 전이라도 끝낼 수 있다
⑦ 원금 12,000 + 이자 1,200 (넣은 돈 기준) · ⭐10
```

### 보강 — 아이가 이자를 **제안**한다

이자를 아이가 고르게 하되 **고르게 해놓고 무시하면 안 된다.** 아이에게 「고르게 해놓고
안 들어줌」은 신뢰를 깎는다. 그래서 「선택」이 아니라 **「제안」**이다.

| | |
| --- | --- |
| `wanted_pct` | 아이가 **바란** 값 |
| `interest_pct` | 실제 적용값 — **보호자가 정한다** |
| 화면 | 누르기 **전에** 「얼마로 할지는 부모님이 정해요」를 말하고, 뒤에 「부모님이 10%로 해주셨어요」로 답한다 |

조용히 넘기면 「왜 물어봤지」가 된다.

### 보강 — 보호자 화면 `/parent/bank/savings`

신청 대기(받아들이기·거절) · 진행 중(남은 날·만기 처리). 받아들일 때 **이 약속에만**
이자율을 올려 줄 수 있다 — 아이가 더 바랐을 때 답하는 자리다.

🔴 **만기 전에는 버튼이 안 보이고, 서버도 다시 막는다.** 화면만 감추면 요청은 그대로 통한다.
🔴 `/parent/bank` 의 「적금 신청과 만기」 배지는 **신청 + 만기 도달**을 함께 센다 —
   만기가 됐는데 부모가 안 누르면 아이 돈이 묶인 채로 남는다.

**되살릴 화면 목록을 공용으로 뺐다** (`lib/revalidate/money.ts`).
액션 파일 안에 있어서 **적금 액션이 그 목록을 못 썼다.** 별까지 움직이는 적금은
`/child/stars` 도 함께 되살린다.

**검증** — 부모 승인까지 한 바퀴 전건 통과.

```
② 신청만으로는 안 묶임        ③ 부모가 10% 로 받아들임(아이가 바란 15% 아님) · ⭐1
④ 만기 전 처리 → 거부         ⑤ 만기 → 원금+이자 1,000원 · ⭐10
⑥ 또 누르면 → 중복 거부
```

## D26 🟠 「소비 내역」에 내역이 없었다 — 집계만 있고 건별 목록이 없다

| | |
| --- | --- |
| 문서 | `REQ-FUNC-013` — **전월 대비 증감액 및 업종별 집계.** `UC-06` 도 「전월 증감액 · 업종별 집계 열람」까지다 |
| 구현 | 그 두 가지만 만들었다. **무엇을 샀는지는 어디에도 없었다** |
| 발견 | 사용자 지적 (2026-09-01) — *"소비 내역에 아이의 소비 내역이 나와야 하는 거 아니야?"* |
| 판단 | **요구사항이 요구하지 않는다.** 그런데 §4.3 추적표의 설계 컴포넌트 이름이 `SpendingLedgerView`(원장 뷰)이고 화면 이름도 「소비 **내역**」이다 |

**요구사항과 이름이 어긋나 있었다.** 합계 4,500원을 보고도 보호자는 무엇을 샀는지 알 수 없다.
데이터는 이미 건별로 다 있었다 — `spending_records` 에 날짜 · 업종 · 금액 · 계획 카드 연결 · 업종 일치.

**한 것** — 집계 아래에 건별 목록을 붙였다. 「9월 1일 · 문구점 · 계획에 없던 업종 · 1,500원」.

**🔴 잘못을 표시하는 목록이 아니다.** 세 문구(「계획에 있었어요」 · 「계획에 없던 업종」 · 「계획 없이」)
전부 **사실 진술**이고 어느 것도 별을 막지 않는다 — ⭐ 판정은 금액 단독이다 (`ADR-008`).
**색으로 가르지 않은 것도 같은 이유다.** 「계획 없이」에 경고색을 쓰면 부모가 아이를 다그치는 화면이 된다 (`P-03`).

**🔴 가게 이름은 넣지 않았다.** 스키마에 `merchant_category` 만 있고 상호가 없다 —
**아이가 어디를 다니는지가 그대로 위치 기록이 된다.** 업종까지가 이 화면의 한계이며,
화면에도 그 이유를 적었다. 「없어서 못 넣었다」가 아니라 **넣지 않기로 한 것**이다.

**집계와 같은 배열에서 만든다** — 따로 조회하면 합계와 목록이 어긋난다. 통장에서 이미 겪었다(`D22-b`).

**할 일** — `REQ-FUNC-013` 에 건별 열람을 추가하거나, 추적표의 `SpendingLedgerView` 를
집계 전용 이름으로 바꾼다. **둘 중 하나는 해야 이름과 내용이 맞는다.**
결제 웹훅(`PTN-002`)이 붙기 전까지 이 목록은 시드 데이터를 보여준다 — 화면이 그렇게 말한다.

## D27 🔴 보호자로 로그인해도 **남의 집 아이**가 나왔다 — 아동 모드가 안 꺼진다

| | |
| --- | --- |
| 문서 | `D5` · `REQ-NF-011` — 아동 모드는 **보호자 PIN 으로 푼다** |
| 구현 | 그 **PIN 화면을 아직 안 만들었다.** 그런데 아동 모드로 들어가는 길(`/child/enter`)만 만들어 뒀다 |
| 어긋남 | 로그인 · 가입 · 로그아웃이 **아동 모드 쿠키를 건드리지 않는다.** 나가는 문이 없다 |
| 발견 | 사용자 지적 (2026-09-01) — *"tester 로 로그인했는데 왜 서연이 나오는 거야"* |

**무슨 일이 났나** — 브라우저에 시드가 만든 아이(`dev-guardian` 의 「서연」)의 기기 토큰이 남아 있었다.
그 상태에서 `test@naver.com` 으로 로그인하니

1. 아이 화면은 **로그인한 보호자가 아니라 기기 토큰**을 본다 → **다른 집 아이**가 나온다
2. `/parent/**` 는 미들웨어가 전부 `/child/locked` 로 돌려보낸다 → **자기 화면에 못 들어간다**
3. 푸는 열쇠인 PIN 화면이 없다 → **쿠키를 손으로 지우는 것 말고 빠져나올 방법이 없다**

**🔴 권한이 샌 것은 아니다.** 보호자 화면은 `currentGuardian()` 으로 매번 다시 판정하고
미들웨어가 막기까지 했다. **본 것은 아이 화면이고, 그 화면은 원래 기기 토큰으로 판정한다** —
아동은 독립 자격증명을 갖지 않기 때문이다(`S5`). 설계대로 동작했는데 **두 신분이 한 브라우저에
동시에 남을 수 있다는 것**을 아무도 막지 않았다.

**한 것** — 로그인 · 가입 · 로그아웃이 아동 모드 쿠키(`ff_device`)와 아이 기기 토큰을 **지운다.**

**왜 로그인이 PIN 을 대신하나** — 비밀번호는 4자리 PIN 보다 강한 증명이다.
보호자임을 비밀번호로 증명했으면 그 기기는 지금부터 보호자 기기다.
아이가 다시 쓰려면 초대 링크를 한 번 더 열면 된다 — `/child/enter` 한 번이다(`D24`).

**할 일** — `D5` 의 **PIN 잠금 해제 화면을 만든다.** 그게 정식 경로이고 지금 것은 임시다.
가족 공용 기기에서 부모가 잠깐 확인할 때마다 아이 기기 등록이 풀리는 것은 정상이 아니다.
`tools/verify_auth.mjs` 에 회귀 검사 5건을 넣었다 — 지우면 잡힌다.

## D28 🟠 **가정을 요구사항으로 읽고 기능을 만들었다** — 「모으기 목표 이자」를 뺀다

| | |
| --- | --- |
| 내가 근거로 든 것 | `§10.1` **A3** — 「보호자는 **위시리스트 목표에 실제로 이자를 준다**」 |
| 그것의 정체 | **[검증 대기] 가정.** 종단 관찰(E10)로 3개월 시점에 참·거짓을 가릴 항목이다 |
| 위시리스트의 진짜 요구사항 | `REQ-FUNC-012` — 목표 금액의 **30 · 70 · 100% 도달 시 각 ⭐1** · 순위 변경 월 1회. **이자는 한 글자도 없다** |
| 발견 | 사용자 지적 (2026-09-01) — *"모으기 목표에 주는 이자는 따로 없지 않았어? 예/적금 시 이자를 주는 거였고 위시리스트는 부모가 후원식으로 지원해주는 걸로 알고 있었는데"* |

**가정 대장은 「검증할 것」을 적는 곳이지 「만들 것」을 적는 곳이 아니다.**
A3 는 3개월 뒤 관찰로 확인할 항목인데, 그것을 화면 기능의 근거로 삼았다.
`§3` 화면 목록에 「이자율 설정」이 있는 것은 맞지만, **그 이자가 무엇에 붙는지는
어느 요구사항에도 없었다.** 빈칸을 A3 로 메운 것이 잘못이다.

**그 기능은 아무 일도 하지 않았다** — 지급 경로 **0건**. 원장에 안 적히고 별도 안 주고
나무도 안 자란다. 「한 번 줄 때 이자 N원」이라는 숫자만 떠 있었고, 주기가 `D6` 미결이라
앞으로도 지급될 계획이 없었다.

**한 것**

- 위시리스트 기반 이자 계산과 표시(`interestWon`)를 **지웠다**
- 이자율의 이름을 **「우리 집 이자율」**로 바꿨다 — 실제 쓰임이 그것이다.
  아이가 「우리 집 적금」(`D25`)을 신청하면 이 값이 그 약속에 박히고 **만기에 실제로 지급된다**
- `REQ-FUNC-012` 의 30 · 70 · 100% ⭐1 은 **그대로다.** `modules/wishlist` 에 이미 있고 건드리지 않았다

**남은 위험** — 아이 화면(`modules/allowance.getPassbook`)도 `savedWon` 으로 이자를 계산해
보여준다. 같은 가정에서 나온 것이므로 아이 화면 쪽에 알렸다.

### D28-b — 이자율 설정 칸 자체를 통장에서 뺐다

이름을 「우리 집 이자율」로 고쳐 놓고 보니, **그 칸이 하는 일이 없었다.**

보호자는 이미 **적금을 승인하는 자리에서 건마다 이자율을 입력한다**
(`/parent/bank/savings` 의 `<input name="pct">`). 통장의 설정 칸은 그 입력란의
**기본값**을 정해 둘 뿐이었다.

**그리고 함정이 있었다.** 이자율은 아이가 **신청하는 순간** 그 약속에 박힌다
(`savings.request`). 그래서 통장에서 이자율을 바꿔도 **이미 올라온 신청은 안 바뀐다** —
보호자는 바꿨다고 믿는데 승인 화면에는 옛 숫자가 그대로 있다.
**같은 값을 두 곳에서 정하게 두면 반드시 갈린다**(`D22` · `D22-b` 와 같은 실수).

**한 것** — 통장에서 이자율 섹션 · `setInterestAction` · `BankView.interestPct` ·
`INTEREST_CHOICES` 를 지웠다. 이자율은 **승인하는 자리 한 곳**에서만 정한다.
참조가 없어진 Server Action 은 남기지 않는다 — 호출 가능한 공개 진입점이 된다(`§6.1`).

**🔴 남은 구멍** — `guardian_accounts.savings_interest_pct` 를 **아무도 쓰지 않는다.**
아이 화면이 「우리 집 이자 N%」로 읽고 `savings.request` 가 기본값으로 쓰는데,
설정 칸이 사라져 값이 갱신되지 않는다. **승인할 때 넣은 이자율을 그 집 기본값으로
함께 저장하면 닫힌다** — `modules/bank.setInterestPct` 를 남겨 뒀고 아이 화면 쪽에 알렸다.

**할 일** — `§3` 화면 목록의 「이자율 설정」을 **적금 승인 화면으로** 옮겨 적는다.
A3 를 검증하려면 관찰 설계를 따로 만든다 — 화면 기능으로 대신하지 않는다.

## D29 🟠 실천이 네 군데로 흩어져 있었고, 퀴즈를 하루에 몰아 풀 수 있었다

| 이전 | 지금 |
| --- | --- |
| 「오늘 해볼 것」이 **영역 화면마다** 따로 | `/child/practice` **4분면 한 화면** |
| 퀴즈를 URL 로 골라 **하루에 4문제** | **하루에 한 문제**, 날짜에서 계산 |

### 실천을 한 화면에 모은다

영역마다 흩어 놓으면 아이는 **네 군데를 돌아다녀야** 하고, 그러면 오늘 무엇을 할지 못 고른다.
벌기 · 잘 쓰기 · 모으기 · 불리기를 나란히 두고 **영역마다 하나씩만** 보여준다 —
읽은 편의 실천을 전부 늘어놓으면 고르는 일이 다시 생긴다. 「오늘 이거 하나」가 실천을 만든다.

| 칸 상태 | 무엇을 보여주나 |
| --- | --- |
| 아직 한 편도 안 읽음 | **「먼저 한 편 읽어요」 → 배우러 가기.** 안 배웠으면 실천할 것이 없다 |
| 할 수 있음 | 오늘의 실천 한 줄 + 「해봤어요 · ⭐1」 |
| 기다리는 중 / 받음 / 거절 | 그대로 말한다 (AC-6.2) |
| 🔴 **불리기** | 미션이 아니라 **저금**으로 실천한다 (D25) → 통장으로 보낸다 |

칸마다 **오늘의 문제** 링크도 둔다. 이미 맞혔으면 「오늘 문제 다 풀었어요」로 바뀐다.

### 퀴즈는 하루에 한 문제

번호를 URL(`?n=`)로 고르게 뒀더니 **하루에 네 문제를 다 풀 수 있었다.**
「매일 조금씩」이 이 제품의 리듬인데 몰아 풀면 그 리듬이 사라진다.

| 규칙 | 어떻게 |
| --- | --- |
| 🔴 날짜에서 계산한다 | DB 에 「오늘 뭐 냈지」를 적으면 자정 경계·기기 시간대마다 어긋난다. 같은 날이면 누가 언제 열어도 같은 문제다 |
| 영역마다 다른 문제 | 슬러그를 섞는다. 안 그러면 네 영역이 늘 같은 번호다 |
| 오늘 맞혔으면 다시 안 낸다 | 별 원장이 답을 갖고 있다(같은 멱등키). 같은 문제를 또 내면 별이 안 붙어 아이가 혼란스럽다 |
| 「다음 문제」를 없앴다 | 있으면 하루에 몰아 푼다 |

🔴 **아직 안 한 것** — 문항이 영역당 4개뿐이라 **4일이면 한 바퀴가 돈다.**
그다음부터는 이미 맞힌 문제만 돌아오고 별이 안 붙는다. 문항을 늘리거나
계산형 템플릿(사용자와 논의한 ①)이 필요하다.

## D30 🔴 미션에 **금액**이 빠져 있었다 — 「벌기」의 실체가 없었다

| 원문 | 실제 |
| --- | --- |
| `REQ-FUNC-002` 미션 루프 — 조건·**금액** 사전 설정 → 승인 → ⭐1 | **금액을 통째로 빠뜨렸다.** `reward` 를 별 개수로 읽고 용돈 경로를 안 만들었다 |

> 보호자는 미션 조건과 **금액**을 사전 설정할 수 있어야 하며, 승인 시 **⭐1**이 지급되고
> 실천 카운트에 가산되어야 한다 — `REQ-FUNC-002`

**둘 다다.** 금액(용돈)과 ⭐1. 사용자가 「미션은 부모가 금액을 걸어두고 완료되면 용돈이
생기는 기능 아니었냐」고 물어서 드러났다.

**왜 이게 큰가** — 미션은 **「벌기」의 실체**다. 심부름을 하고 용돈을 받는 것이
아이가 겪는 **유일한 「버는」 경험**인데, 별만 주면 학습과 정면으로 어긋난다.
`earn-3`「용돈은 내가 번 돈일까?」가 **「심부름을 하고 받았거나 안 쓰는 물건을 팔아서
생긴 돈이 내가 번 돈이에요」**라고 가르치는데, 앱에서 심부름을 하면 별만 나왔다.

**고친 것**

| | |
| --- | --- |
| `missions.payout_won` 신설 | 승인 시 **용돈 원장에 `TOPUP`** 으로 들어간다 |
| ⭐를 **1로 고정** | `REQ-FUNC-002` 가 못박았다. 값은 금액으로 매긴다 |
| 보호자 폼 | 「해내면 줄 별」 → **「해내면 줄 용돈」** |
| 아이 화면 | 「2,000원 · ⭐1」로 함께 보여준다. 별만 보이면 「벌기」가 안 보인다 |

🔴 **별↔현금 전환이 아니다** (P-21 · REQ-NF-010). 보호자가 **일한 대가로 용돈을 주는 것**이고,
실제 돈은 앱 밖에서 오간다 — 원장은 그 사실을 적을 뿐이다(D18). 별은 여전히
방 꾸미기에만 쓰이고, 두 원장 사이에 전환 함수는 없다.

🔴 **학습에서 온 실천에는 금액이 없다** (`payoutWon: 0`). 아이가 자기 실천에 금액을
정하면 그건 용돈이 아니다. 부모가 만든 미션에만 금액이 붙는다.

**검증** — 실제 DB 대상 전건 통과.

```
① 부모가 「분리수거 돕기 · 2,000원 · ⭐1」 만듦 → 아무것도 안 생김
② 아이가 「했어요」 → 여전히 안 생김
③ 부모 승인 → ⭐+1 · 용돈 +2,000원
④ 또 승인 → P2002 거부 · 용돈 그대로 (두 번 안 들어감)
⑤ 학습에서 온 실천 → 금액 0원
```

🔴 **다시 볼 것** — 기존 미션의 `reward`(1~5)를 `reward × 500원` 으로 옮겼다.
시연 데이터라 문제없지만 **운영 데이터에는 이 환산을 쓰면 안 된다.**

- **`cache-control: no-store`** — 판정하면 원본이 사라지는데 브라우저·CDN 에 남으면

**검증** — `verify_mission_loop` 에 넣은 것은 「사진 표가 비었나」가 **아니라**
**「판정된 미션 중 사진 있는 것이 0건인가」**다. 전체 0건으로 재면

## D33 🔴 초대 링크가 **오래 사는 자격증명을 주소에 싣던 것**을 닫는다 — `D24` 해소

| | |
| --- | --- |
| `D24` | 「`/child/enter?t=` 가 180일짜리 기기 토큰 자체를 주소에 싣는다」 — 운영 전 필수로 올려 뒀다 |
| 새 사양 | `FR-002` — **1회용 토큰 · TTL 24시간 · 첫 실행 시 소진 처리** |
| 상태 | **닫혔다.** 지적한 것이 그대로 요구사항이 됐다 |

**주소에 실리는 것이 더 이상 자격증명이 아니다.** 24시간짜리 1회용 코드이고,
기기 토큰은 `/child/enter` 가 그 코드를 **교환해서 그 자리에서 새로 발급**한다.
코드가 새도 이미 쓰인 것은 쓸모가 없다.

### 지키는 선

- **원문을 저장하지 않는다** — 해시만 남기므로 DB 가 새도 링크는 새지 않는다
- **소진이 원자적이다** — `update … where used_at is null and expires_at > now()` **한 문장**.
  「읽고 → 검사하고 → 표시한다」로 나누면 두 기기가 동시에 열 때 **둘 다 통과**한다
- **새로 만들면 앞의 미사용 코드가 죽는다.** 링크가 여러 장 돌아다니면
  보호자는 어느 것이 살아 있는지 알 수 없다
- **동의를 철회하면 전부 무효**다 (`AC-002-4`). 진입 판정에서도 동의를 다시 보지만,
  철회 뒤에 **기기 등록이 성립하는 것 자체**를 두면 「등록은 됐는데 화면은 잠김」이 된다
- **왜 틀렸는지 구별해 돌려준다** — `EXPIRED`(다시 요청해요)와 `USED`(이미 연결됨)는
  아이에게 **다른 말**이어야 한다 (`AC-002-2`)

### 길을 하나로 합쳤다

부모 화면의 「기기 등록」이 **그 자리에서 기기 토큰을 심던 것**을 없애고,
초대 코드를 발급해 `/child/enter` 로 보낸다. **같은 기기든 아이 기기든 같은 길**이다
(`AC-002-3`). 길이 둘이면 한쪽만 고쳐지고, 실제로 그랬다.

**보호자 세션 종료가 `/child/enter` 로 옮겨간다** — 기기가 실제로 아이 것이 되는 순간이
거기다. 안 끝내면 아이 손에 살아 있는 보호자 세션이 쥐어진다.

**🔴 `S5` 위반이 아니다.** 링크를 만드는 주체는 보호자이고 아이는 아무것도 입력하지 않는다.
바뀐 것은 **자격증명 전달 방법**이지 인증 모델이 아니다.

**할 일** — `SRS §6.1` 진입점 표에 `/child/enter` 를 올린다. 지금 표에 없는 진입점이다.
개발용 링크 생성 스크립트(`prisma/issue-link.mjs`)가 `issueInvite` 를 쓰게 바꾼다 —
이제 링크는 24시간에 한 번 쓰면 죽는다.

## D33 보강 — `/child/enter` 를 1회용 코드로 바꿨다

라우트는 이쪽 것이라 이쪽이 고쳤다. `consumeInvite(token)` 하나만 부른다.

| 규칙 | 왜 |
| --- | --- |
| 🔴 **보호자 세션을 여기서 끝낸다** | 기기가 실제로 아이 것이 되는 순간이 여기다. 안 끝내면 **아이 손에 살아 있는 보호자 세션**이 쥐어진다. 쿠키만 지우면 서버 세션이 살아 있으므로 `closeSession` 을 부른다 |
| 🔴 **사유를 뭉뚱그리지 않는다** (`AC-002-2`) | 「만료」는 다시 요청해야 하고 「이미 연결됨」은 이미 된 것이다. 같은 말을 하면 아이가 뭘 해야 할지 모른다 |
| 부모 기기도 같은 길로 | 길이 둘이면 한쪽만 고쳐진다 (`AC-002-3`) |

**개발용 발급기도 바꿨다** — `issue-link.mjs` 가 초대 코드를 낸다.
**24시간 · 한 번만 열린다.** 확인할 때마다 다시 돌려야 한다.

**검증** — 첫 번째 열기 → 내 방 · 두 번째 → `reason=USED` · 없는 코드 → `reason=NOT_FOUND`.

## D34 🟠 봉투형 소비 관리 — 계획 카드 옆에 세운다

`FR-020`(봉투 배분) · `FR-021`(결제 자동 대조 · ⭐ 판정). 새 문서의 소비 모델이다.

| | 계획 카드 (옛 문서) | 봉투 (새 문서) |
| --- | --- | --- |
| 언제 | 나갈 때마다 한 건씩 적는다 | **충전할 때 미리** 용도별로 나눠 담는다 |
| 대조 | 아이가 「얼마 썼는지」를 적는다 | **결제가 오면 업종으로 봉투를 골라** 자동 차감 |
| ⭐ | 금액을 지켰으면 준다 | **결제 시각의 배분 스냅샷** 기준 |

### 🔴 스냅샷이 이 기능의 핵심이다

`AC-021-3` — 결제 뒤에 아이가 봉투를 5,000원으로 늘려도 **직전 판정이 안 바뀐다.**
사후 수정이 소급되면 「계획대로 썼다」가 무의미해진다. 그래서 결제 행이
**그 시각의 한도(`snap_allocated`)와 잔액(`snap_remaining`)을 자기 안에 박아 둔다.**

### 지킨 규칙

| 규칙 | 어떻게 |
| --- | --- |
| 🔴 **넘어도 결제는 통과** (`AC-021-2`) | 아이를 매장에서 세우지 않는다 — 앱은 카드가 아니라 **장부**다. ⭐ 미지급으로만 말한다 |
| 🔴 넘겼다고 **깎지 않는다** | 미지급일 뿐이다 (P-03) |
| 🔴 봉투 간 **자동 이동 없음** | 앱이 마음대로 옮기면 아이는 자기 배분을 못 믿는다 |
| 🔴 합계 > 쓸 수 있는 돈 → **저장 거부** (`AC-020-1`) | 안 그러면 **없는 돈을 담은 화면**이 된다 |
| 🔴 미분류 봉투는 아이당 **하나** | 둘이면 업종을 못 고른 결제가 어디로 갈지 알 수 없다 (DB 부분 유니크) |
| 🔴 한 거래는 **한 번만** 빠진다 | 웹훅이 두 번 와도 두 번 안 빠진다 (`txn_id` 유니크) |
| 재배분 이력을 남긴다 (`AC-020-3`) | 다그치려는 게 아니라 **부모가 바뀐 걸 아는** 장치다 |
| 음수를 안 보여준다 | 넘긴 봉투도 「0원 남음」이 아니라 **「700원 넘었어요」**. 음수는 아이가 **빚**으로 읽는다 |

### 🔴 계획 카드를 지우지 않았다

`spending_records.plan_card_id` · `category_match` 를 읽는 **부모 소비 내역이 있다.**
지우면 그 화면이 깨지고, 계획 카드로 만든 **옛 기록도 못 읽는다.**
**컬럼을 더했다** — 새 기록은 봉투로, 옛 기록은 계획으로 읽는다.

### 결제 웹훅이 없다

`FR-021` 입력은 발행사 웹훅인데 제휴가 없다. **예시 거래(`source=MOCK`)로 흐름을 세우고**
화면이 「카드 연결 전이라 예시 데이터입니다」를 밝힌다. 실제 웹훅이 붙으면 입력만 바뀐다.

**검증** — 실제 DB 대상 전건 통과.

```
② 쓸 수 있는 돈보다 많이 담기 → 거부                  (AC-020-1)
④ 간식 3,000 · 편의점 1,200 → 봉투 안 · ⭐1 · 1,800원 남음  (AC-021-1)
⑤ 분식집 2,500 → 700원 넘음 · ⭐ 없음 · **결제는 통과**     (AC-021-2)
⑥ 봉투를 10,000원으로 고침 → 직전 판정 그대로 · 스냅샷 3,000원 (AC-021-3)
⑦ 업종 모르는 결제 → 미분류 봉투에서 차감
```

### 🔴 보강 — 돈 화면이 넷이 되어 있었다

봉투를 만들자 아이가 보는 돈 화면이 **넷**이 됐다 — 통장 · 봉투 · 지난 계획 카드 ·
갖고 싶은 것. 사용자가 「봉투 나누니까 작업이 더 복잡해진 것 같은데?」라고 지적했다.
**맞았다.**

원인은 봉투 자체가 아니라 **옛것과 새것이 같이 살아 있어서**였다.
소비를 적는 곳이 둘(`spending_records` · `envelope_spends`)이었고,
⭐ 판정 기준도 둘(계획 한도 vs 봉투 잔액)이었다.

**통장 하나로 합쳤다** (2026-09-01 사용자 결정).

| 접은 것 | 어디로 |
| --- | --- |
| `/child/envelopes` | **통장 안 「봉투」 구역** |
| `/child/plan` · `/child/plan/new` | 없앴다 — 봉투가 그 자리다 |
| `/child/retro/[recordId]` | 없앴다 — 봉투의 「700원 넘었어요 · 다음엔 얼마로 할까요?」가 회고를 대신한다 |

**아이가 보는 돈 화면은 둘이다** — 내 통장 · 갖고 싶은 것.

🔴 **`spending_records` 와 옛 기록은 남긴다.** 부모 소비 내역이 읽고, 지우면 지난
데이터가 사라진다. **쓰기만 멈췄다** — `createPlanCard` · `recordActual` 을 없앴다.

🔴 **`spending_records` 에 더했던 봉투 컬럼 셋을 되돌렸다.** 봉투 결제는
`envelope_spends` 에 쌓이므로 **아무도 안 썼다.** 두 표에 같은 뜻의 칸이 있으면
다음 사람이 「어느 쪽이 진짜지」를 묻는다 — 잔액에서 세 번 겪은 것과 같은 모양이다.

🔴 **봉투에 담은 돈을 합계에 더하지 않는다.** 그 돈은 **「쓸 수 있는 돈」 안에** 있다 —
따로 더하면 두 번 센다. 담아 둔 몫만 옆에 갈라 보여준다.

### 보강 — 봉투가 맡는 업종을 고칠 수 있게 했다

문서에 없는 것이지만 **없으면 봉투가 반쪽이다.** 봉투가 맡는 업종이 만들 때 박혀 있어서
아이가 **새 봉투를 만들어도 아무 결제가 안 걸렸다.** 이름도 그림도 못 바꿨다.

| 규칙 | 왜 |
| --- | --- |
| 🔴 **한 업종은 한 봉투만 맡는다** | 둘이 같은 업종을 맡으면 결제가 **코드가 먼저 찾은 쪽**으로 간다 — 아이가 이유를 알 수 없다. 그래서 다른 봉투에서 **떼어 온다** |
| 🔴 미분류 봉투는 업종을 안 갖는다 | 나머지를 전부 받는 자리다. 업종을 붙이면 「나머지」의 뜻이 사라진다 |
| 🔴 미분류 봉투는 못 지운다 | 지우면 업종을 못 고른 결제가 **갈 곳이 없다** |
| 지워도 쓴 기록은 남는다 | 봉투만 끊는다. 지우면 지난 소비가 사라진다 |
| 업종이 비면 그 사실을 말한다 | 「정하지 않으면 이 봉투로 아무것도 안 들어와요」 — 조용히 두면 아이는 고장 난 줄 안다 |

### 보강 — MCC 표를 넣었다 (`DAT-004` 의 자리)

**실제 카드가 보내는 것은 MCC**(ISO 18245 네 자리)다. 예시 거래에 우리 업종 4종을
직접 박아 넣고 있었는데 **그건 실제 입력이 아니었다.** 웹훅이 붙었을 때 바꿀 코드를
줄이려면 지금부터 MCC 를 받아 접어야 한다.

`contracts/mcc.ts` — 확실히 아는 코드만 적었다. 애매하면 넣지 않았다.

| | |
| --- | --- |
| 간식·음료 | `5411` 식료품점 · `5441` 사탕·과자 · `5462` 제과점 · `5499` 편의점 · `5812` 음식점 · `5814` 패스트푸드 … |
| 문구 | `5943` 문구·사무용품 · `5111` 사무용품 · `5972` 우표·수집품 |
| 도서 | `5942` 서점 · `5192` 도서·정기간행물 · `5994` 신문 |
| 선물·장난감 | `5945` 완구·게임 · `5947` 선물·기념품 · `5970` 미술·공예 · `5641` 아동복 … |

### 🔴 포괄 코드를 **일부러 미분류로 보낸다**

`5331`(잡화점) · `5399`(기타 종합 소매) · `5999`(기타 소매) · `5310`(할인점) 같은 코드는
**무엇을 샀는지 알 수 없다.** 한국은 동네 가게가 이런 코드로 뭉뚱그려 들어오는 일이 흔하다.

이런 결제를 문구 봉투에서 빼면 아이가 **「왜 여기서 빠졌지」**를 묻는데 답할 수 없다.
**틀린 분류보다 「모르겠어요」가 낫다** — 미분류 봉투로 보내고 부모가 고치게 한다.

시드가 **다이소를 일부러 `5331`** 로 둔다. 시연에서 이 경우가 보여야 한다.

| 가맹점 | MCC | 접은 업종 | 갈 봉투 |
| --- | --- | --- | --- |
| 편의점 | `5499` | SNACK | 🍬 간식 |
| 동네 서점 | `5942` | BOOK | 📚 책 |
| 학교 앞 문구점 | `5943` | STATIONERY | 🖊 문구 |
| **다이소 성수점** | `5331` | **(모름)** | 📦 그 밖에 |

**어느 봉투로 갈지 누르기 전에 보여준다** — 「편의점·기타 식품 → 간식」. 눌러 보고 아는 건 늦다.

### 🔴 이 표만으로는 90% 를 못 채운다

**코드값은 표준이라 틀리지 않는다.** 그런데 **어느 가게에 어느 코드가 붙는지는 매입사가 정한다.**
같은 문구점이 매입사에 따라 `5943` 일 수도 `5399` 일 수도 있다.

그래서 표를 아무리 다듬어도 **오분류는 남는다.** 진짜 답은 **보호자가 고친 것이 다음부터
반영되는 길**(가맹점별 교정)이고, 그게 이 표보다 중요하다. 🔴 **아직 없다.**

### 🔴 업종 사전이 없다 — `AC-021-4` 가 측정 불가인 진짜 이유

지금 업종은 계획 카드 때 임시로 넣은 **4종**뿐이다(`STATIONERY`·`SNACK`·`BOOK`·`GIFT`).
코드 주석도 「사전은 `DAT-004` 가 채운다」고 적혀 있다.

**실제 카드는 가맹점 업종 코드(MCC)를 주는데 수백 종이다.** 그걸 이 넷으로 접는 표가 없다.
문서도 알고 있다 — `NFR-024`(매칭 정확도 ≥90%)를 **「모의 결제 β에서는 측정 불가 · 제휴 후
검증」**으로 두고, **가맹점 분류 상세도를 카드사 선정 기준**으로 삼는다고 적었다.

즉 이 기능의 정확도는 **우리 코드가 아니라 어느 카드사와 계약하느냐**에 달려 있다.

🔴 **아직 안 한 것** — 부모 화면의 **초과 알림**(「간식 봉투 700원 초과」)과 **분류 요청**은
부모 쪽이라 그쪽에 남겨 뒀다. 조회 함수(`listReallocations` · `recentSpends`)는 내줬다.

## D35 🔴 소비가 **두 표에 따로 쌓인다** — 부모 화면이 둘 다 읽는다

| | |
| --- | --- |
| 봉투 경로 | `modules/envelope.settlePayment` → `activity.envelope_spends` (`FR-020·021` · 지금 경로) |
| 계획 카드 경로 | `modules/plan.recordSpending` → `activity.spending_records` (봉투 이전 · **아직 살아 있다**) |
| 증상 | `/parent/spending` 이 `spending_records` 만 읽어 **봉투로 쓴 돈이 부모 화면에 아예 안 나온다** |

**잔액에서 세 번 겪은 것과 같은 모양이다** (`D22` 컬럼 vs 원장 · `D22-b` 잔액 개념 둘 ·
`D28-b` 이자율 설정 두 곳). 이번에는 **표가 둘**이다.

**내 요청이 혼선을 만들었다** — 「`spending_records` 에 봉투 컬럼을 더해 달라」고 부탁했는데,
아이 화면 쪽은 새 표를 만드는 쪽이 맞았다. 그래서 `spending_records.envelope_id` ·
`envelope_over` · `unclassified` **세 컬럼을 아무도 쓰지 않는다.**

### 한 것 — 부모 화면이 둘 다 읽는다

지우면 8월 기록 4건이 사라지고, 한쪽만 읽으면 봉투 소비가 안 보인다. **둘 다 읽고 구별해 말한다.**

| 기록 | 문구 |
| --- | --- |
| 봉투 · 안에서 씀 | 「🍪 간식 봉투에서 썼어요」 |
| 봉투 · 넘김 | 「🍪 간식 봉투를 **700원 넘었어요**」 |
| 봉투 · 미분류 | 「어느 봉투인지 몰라요」 |
| 계획 카드(옛것) | 「계획에 있었어요 / 계획에 없던 업종 / 계획 없이」 + **「봉투 이전 기록」** |

🔴 **넘긴 금액을 음수로 쓰지 않는다.** 「−700원」은 아이도 부모도 **빚**으로 읽는다.
🔴 **넘긴 것은 잘못이 아니다.** 결제는 통과했고 ⭐만 안 나갔다 (`AC-021-2`) —
화면이 그 사실을 함께 말한다.

**합계도 두 표를 함께 센다.** 목록만 합치고 합계를 한쪽만 세면
「4,500원인데 줄을 더하면 5,700원」이 된다 — `D22-b` 에서 겪은 실수다.
업종별 집계도 합친다. 두 경로가 같은 업종 코드를 쓰므로 그대로 더해진다.

지울 표가 **27개**다. 하나만 빠뜨려도 아이 기록이 남는데,

- **한 트랜잭션이다.** 중간에 죽으면 절반만 지워진 계정이 남고,

  「환불해 드립니다」라고 쓰면 우리가 못 지키는 약속이 된다

  공개 엔드포인트와 동등하다 — 폼을 우회한 호출로 계정이 지워지면 안 된다

  아이 기기 쿠키도 지운다 — 남으면 지워진 아이를 계속 가리킨다

### 무엇을 잃는지 숫자로 보여준다

`AC-041-1` 이 요구하는 것은 *"모은 별과 나무는 되돌릴 수 없어요"* 가 **진행 전에** 뜨는 것이다.
「기록이 삭제됩니다」로는 **크기가 감춰진다.** 확인 화면이 ⭐ 몇 개 · 나무 몇 칸 ·
미션 몇 개 · 남은 용돈 얼마인지를 먼저 보여준다.

마이페이지에서 **바로 실행되지 않는다.** 확인 화면을 한 번 거치고, 그래서 버튼이 아니라 링크다 —
되돌릴 수 없는 일은 실수로 눌릴 수 있는 자리에 두지 않는다.

**🔴 「비식별 집계치만 잔존」은 아직 못 지킨다.** 집계 표가 없어서 지금은 **전부 파기**다.
`app_events` 도 `child_id` 를 갖고 있어 식별 가능하므로 함께 지운다.
집계 표가 생기면 그때 **집계를 먼저 남기고 원본을 지우는** 순서로 바꾼다.
지금은 **더 지우는 쪽**이라 요구를 어기지 않는다.

**아이가 잘못한 게 아닌데 어제 본 별이 오늘 줄면 아이는 이 앱을 못 믿는다.**

**지급도 멈추지 않는다.** 한 줄이 어긋났다고 오늘 받을 별을 막으면 벌을 주는 셈이다.

**어긋난 줄 다음은 그 줄의 값을 믿고 이어 센다.** 누적합을 고집하면 한 줄 때문에
뒤 줄이 전부 어긋난 것으로 보인다.

**「온콜 알림」은 못 만들었다** — 알림 인프라가 없다. 나무 화면에 표시하는 것으로 대신한다.
없는 것을 있는 척하지 않는다.

### 🔴 검증이 진짜 버그를 잡았다 — 날짜 컬럼에 로컬 자정

`tree_states.cycle_started_at` 은 **`date` 컬럼**이다. 여기에 로컬 자정
(`new Date(2026, 8, 1)` = KST 9월 1일 00시)을 넣으면 그 순간은 UTC 로 **8월 31일 15시**라,
Postgres 가 날짜만 잘라 **8월 31일**을 저장한다. **9월로 넘겼는데 8월로 적힌다.**

그래서 주기 전환이 **매번 다시 일어나고**, 나무가 계속 비워졌다.
`Date.UTC` 로 쓰고 **연·월 문자열로 견주게** 고쳤다. `ensureTreeStates` 도 같은 함정이었다.

**검증을 안 썼으면 못 봤다.** 화면에는 아무 오류도 안 나고 나무만 조용히 비워진다.

### 실행 시점

세 함수 모두 **나무·숲 화면을 열 때** 부른다 (`rollCycleIfNeeded` · `reconcileStars`).
`pg_cron` 이 붙으면 배치가 같은 함수를 부르면 되고 화면은 안 바뀐다.
**단점** — 아무도 화면을 안 열면 돌지 않는다. 시연에서는 문제없고 운영에는 cron 이 필요하다.

**할 일** — `SRS §6.1` 의 `/api/cron/cycle-reset` · `/api/cron/star-reconcile` 를 이 함수에 잇는다.
지난달 스냅샷의 **학습·퀴즈 수가 실제보다 높게 잡힐 수 있다** — 주기별 학습 기록이 없어

「안 적어도 괜찮아요. 내일 다시 물어볼게요」를 같이 보여주는 이유다.

### 🔴 서버 액션이 열려 있었다

`setSchoolEndAction(childId, guardianId, clock)` 이 `guardianId` 를 **인자로** 받고

### 🔴 PIN 은 비밀번호가 아니다 — 그에 맞게 만든다

네 자리는 **10,000가지뿐**이고, **아이가 옆에서 눌러 보는 상황**이 전제다.

| | |
| --- | --- |
| 쉬운 값을 막는다 | `0000` · `1234` · `9876` — 아이가 첫 번째로 눌러 본다. 안 막으면 **잠금이 아니라 장식**이다 |
| 다섯 번이면 잠근다 | 잠긴 뒤에는 **비밀번호로만** 푼다 |
| 잠김은 **기기별**이다 | 보호자에 세면 다른 기기에서 틀린 것까지 합쳐진다. 잠겨야 하는 것은 **그 기기**다 |
| 해제는 **10분**이다 | 영구히 풀면 아이 손에 열린 부모 화면이 남는다 (`S5`) |
| 원문을 저장하지 않는다 | 비밀번호와 같은 `scrypt salt:key` |
| 길이가 달라도 안 던진다 | `timingSafeEqual` 은 길이가 다르면 예외를 낸다 — 먼저 본다 |

### 해제 쿠키만으로는 아무것도 못 한다

미들웨어가 `ff_unlock` 을 보고 통과시키지만 **그것은 1차 관문일 뿐**이다.
각 화면과 Server Action 이 첫 줄에서 **보호자 세션을 다시 본다**(`§6.6` 규약 ②) —
쿠키를 손으로 만들어 넣어도 세션이 없으면 아무것도 열리지 않는다.

미들웨어는 쿠키 **이름만** 안다. `child-mode-pin` 을 import 하면 Edge 런타임이 DB 를 물어 깨진다.

부모가 **거기서 할 수 있는 일이 없었다.** `/parent/plan/new` 를 만들었다.

**「부모가 예산을 정해 준다」로 읽히면 안 된다.** 계획 카드는 아이가 적는
것이고, 이 화면은 **한 장을 같이 적어 보는 자리**다 — 아이가 계획 카드가
뭔지 모르는 채로 시작하지 않게 하려는 것이다. 문구가 그 차이를 말한다.

    "아이와 함께 한 장만 적어 보세요. 다음부터는 아이가 자기 화면에서 적습니다."

`author: "보호자"` 로 남긴다. 지우면 나중에 **아이의 실천을 셀 때 부모가 적은
것까지 섞인다.** 화면이 미리 그렇게 남는다고 말한다.

`childId` 는 **폼에서 받지 않는다.** 세션의 보호자에게서 찾는다 —
받으면 남의 아이 이름으로 계획 카드를 만들 수 있다(`setSchoolEndAction` 과 같은 이유).

### 🔴 ③ 다 끝낸 사람이 **매번 할 일 목록을 지나야** 했다

로그인 뒤 착지가 언제나 `/parent/onboarding` 이었다. 여섯 단계가 모두 ✓ 인
사람이 로그인할 때마다 **✓ 여섯 개짜리 화면**을 봤다 — 매일 쓰는 사람에게는
그게 앱의 첫인상이다.

    guardianLanding(guardianId)  →  다 끝났으면 /parent/tree, 아니면 /parent/onboarding

**판단을 한 곳에 둔다.** 로그인 액션(`signInAction`)과 로그인 화면
(`/login`) 두 군데가 각자 정하면 한쪽만 고쳐져 갈라진다.

단계 키를 나열하지 않고 `Object.values(p).every(Boolean)` 로 센다 —
**단계가 늘면 나열한 곳도 같이 늘려야 하는데, 반드시 잊는다.**

### 실제로 확인한 것

실 DB(`finfriends`)의 보호자 세 계정으로 봤다.

    카드 ACTIVE   6/6  → /parent/tree
    카드 SHIPPING 6/6  → /parent/tree     ← 발급 전에도 넘어간다
    카드 없음     3/6  → /parent/onboarding

카드 상태를 바꿔 본 계정은 **원래 값으로 되돌렸다.**

### 곁들여 — `/child/locked` 에 어른 자리로 가는 길

`D42` 가 `/unlock` 을 만들었다. 아이가 보는 화면이라 **「PIN」도 「잠금」도
안 쓰고** 「부모님이신가요?」로 **묻는 형태**로 뒀다 — 아이를 밀어내는 말이
되지 않게. PIN 이 없는 집이면 `/unlock` 이 정하는 법을 안내한다.

    ALTER TABLE activity.learning_progress ADD COLUMN last_read_day TEXT;

**KST 날짜 문자열**로 담는다. `timestamptz` 면 「오늘」을 물을 때마다 시간대를
되돌려야 하고 서버가 어디서 도는지에 따라 경계가 흔들린다. `kstDay()` 값 그대로다.

**새 편을 읽은 날만 찍는다.** 복습으로 날짜가 밀리면 「오늘 읽을 편」이 영영 안 나온다.

### 🔴 세 곳에서 같은 답이 나와야 한다

화면에서 회색으로 칠하는 것만으로는 안 된다 — **주소를 직접 치면 그대로 열린다**
(SRS-Tech §6.6). 판단을 `getLessonList` 하나에 두고 세 곳이 그걸 본다.

    목록 화면      locked 면 링크가 아니라 <div> 로 그린다 (누를 수 없다)
    상세 화면      locked 면 본문 대신 🔒 안내
    finishLessonAction   canOpenLesson() 로 다시 본다 — 폼은 주소만 알면 던진다

실천도 같다. `claimPractice` 가 **서버에서** 하루 하나를 막고,
화면은 버튼 대신 「오늘 실천 다 했어요」를 그린다 —
**눌리지 않는 버튼이 제일 나쁘다.**

### 읽기 다음은 **문제**다

    전   다 읽었어요 → 다음 편 → 다음 편 → … → 마지막에야 퀴즈
    후   다 읽었어요 · 오늘의 문제로 → 퀴즈

버튼이 어디로 가는지 **미리 말한다.** 눌러 보고 아는 건 늦다.

### 🔴 「그만해」로 들리면 안 된다

오늘 몫을 다 한 것은 **잘한 것**이다. 잠긴 것을 회색으로만 두면 아이는
「고장났나」로 읽는다. 왜 못 여는지와 언제 열리는지를 같이 적는다.

    "오늘 읽기는 다 했어요. 내일 새 이야기가 와요."
    "이야기는 하루에 한 편씩 열려요."          목록 아래 늘 보인다
    "내일 열려요" · 🔒                         잠긴 편마다
    "✓ 오늘 실천 다 했어요 / 내일 새 이야기가 와요"

### 실제로 확인한 것

실 DB 의 「루프 · 벌기」로 `last_read_day` 를 바꿔 가며 봤다.

    lastReadDay = null          오늘 읽을 편 있음
    lastReadDay = 오늘          오늘 읽을 편 없음 · 나머지 🔒
    lastReadDay = 어제          오늘 새 편 열림

바꾼 값은 **원래대로 되돌렸다.**

## D48 🔴 미션 사진 — **찍을 수도, 완료 뒤에 붙일 수도 없었다** (`FR-032`)

| | |
| --- | --- |
| 새 SRS | `FR-032` 미션 사진 — **선택** · 판정 즉시 파기 |
| 우리 | 저장 경로는 다 있었는데 **아이가 도달할 수 없었다** |
| 결정 | 사용자 (2026-09-01) — *"아이가 미션을 완료후 사진을 찍을수 없는거 아니야"* |

표에 사진이 **0건**이었다. 기능이 없어서가 아니라 **길이 막혀 있어서**였다.

### 🔴 ① 완료 뒤에 붙일 길이 **아예 없었다**

사진칸이 「했어요」 버튼과 **같은 폼**에만 있었다. 한 번 누르면 미션이 `WAITING`
으로 가고, 그 칸에는 **「아니에요」밖에 없다.**

    아이가 하는 순서   미션을 한다 → 했어요 → 사진 찍는다 → 붙일 데가 없다
    화면이 요구한 순서  사진을 미리 찍어 둔다 → 했어요

**후자는 어른의 순서다.** 아이는 하고 나서 찍는다.
되돌리려면 「아니에요」로 취소했다가 다시 올려야 했는데, 그건 아이가 스스로
찾아낼 방법이 아니다.

`attachMissionPhoto` 를 따로 두고 `WAITING` 칸에 붙였다.
`attachPhoto` 가 **판정 전(`PENDING`)인지 다시 본다** — 부모가 이미 본 미션에
사진이 뒤에서 붙으면 판정 근거가 바뀐다.

### 🔴 ② iOS 에서 **카메라가 안 떴다**

    전  accept="image/jpeg,image/png,image/webp"
    후  accept="image/*"

서버가 받는 형식을 화면에 그대로 옮겨 적은 것인데, **iOS 사파리는 MIME 을
하나하나 적으면 「사진 찍기」를 안 띄운다** — 파일 고르기만 나온다.
**아이 폰에서는 찍을 수가 없었다는 뜻이다.**

형식 검사는 서버가 이미 한다(`PHOTO_MIME`). 화면은 **고르는 문을 여는 역할**이지
검사하는 자리가 아니다. `capture` 는 여전히 안 넣는다 — 강제 촬영은 요구가 아니고
이미 찍어 둔 사진도 고를 수 있어야 한다.

### 🔴 ③ `hasPhoto` 가 **`false` 로 박혀 있었다**

계약에 필드가 있고 화면도 받을 준비가 돼 있었는데 `toView` 가 상수를 넣고 있었다.
**아이가 자기 사진이 올라갔는지 알 길이 없었다** — 「올라갔나?」 싶으면 또 올리는 것
말고는 확인할 방법이 없다.

`mission_photos` 는 Prisma 관계가 없어서(`mission_id` 만 갖는다) **조인이 아니라
id 만 따로 센다.** 관계를 걸면 FK 가 생기고 마이그레이션이 필요하다.
**`bytes` 를 절대 안 읽는 것**도 중요하다 — 목록에 사진 원본이 딸려 오면 안 된다.

### 실패를 조용히 넘기지 않는다

    ok         "사진을 보여줬어요. 부모님이 보시면 바로 지워져요."
    BAD_MIME   "이 사진은 못 올려요. 사진으로 다시 찍어 볼래요?"
    TOO_LARGE  "사진이 너무 커요. 조금 작게 찍어 볼래요?"

「안 돼요」로 끝내지 않고 **다음에 뭘 할지** 적는다(`ACE-1.1`).

### 실제로 확인한 것

실 DB 에 판정 전 미션을 만들고 1×1 PNG 로 전 구간을 돌렸다.

    붙이기 전 hasPhoto  false
    PNG 붙이기          ok      → image/png · 70바이트 저장
    붙인 뒤 hasPhoto    true
    gif                 BAD_MIME
    빈 파일             EMPTY
    판정 뒤             NOT_FOUND   ← 판정 근거가 뒤에서 안 바뀐다

검증용 미션과 사진은 **지웠다.** 남은 사진 0건.

## D49 🔴 사진을 **벌기 부모 미션에서만** 받는다 — `FR-032` 「선택」에서 벗어난다

| | |
| --- | --- |
| 새 SRS | `FR-032` — 미션 사진은 **선택**이다 |
| 우리 | **벌기 · 부모가 준 미션은 필수**, 나머지는 **사진칸 자체를 안 보여준다** |
| 결정 | 사용자 (2026-09-01) — *"벌기 부모님이 준 미션에서만 … 사진을 보내야 하는거야, 잘쓰기는 카드 내역만 확인하면 되니까"* |

**요건에서 벗어나는 방향이다.** `FR-032` 는 선택이라고 못박았고 코드 주석도
「찍을 수 없는 실천(참기·기록하기)이 있어서 필수로 하면 아예 못 올린다」였다.
그 반론을 전하고 사용자가 결정했다.

### 🔴 기준은 **앱이 볼 수 있느냐**다

    벌기 · 부모 미션   집안일 · 심부름 — **앱이 볼 수 없다.** 사진이 유일한 증거
    잘 쓰기            카드 결제 내역이 답한다
    모으기             통장 · 위시리스트 잔액이 답한다
    불리기             적금 회차가 답한다
    배워서 한 것        아이가 스스로 고른 실천이다 — 부모가 시킨 일이 아니다

**앱이 이미 아는 것을 아이한테 다시 찍어 오라고 하지 않는다.**
예전엔 **모든 미션에 사진칸이 나왔다** — 카드로 산 젤리를 찍어 오라는 셈이었다.

### 판단은 계약에 둔다

    contracts/mission.ts   needsPhoto(topic, fromLesson)

아이 화면 · 서버 액션이 **같은 함수**를 본다. 갈라지면 아이는 사진칸이 없는데
서버는 사진을 기다리거나, 반대가 된다.

### 🔴 필수는 **올리기 전에** 본다

올린 뒤에 막으면 아이가 한 일이 「기다리는 중」에 **사진 없이** 남고 부모는
판정할 근거가 없다. `findForPhoto()` 로 규칙만 먼저 보고, 통과해야 `markDone` 한다.

`bytes` 를 안 읽는다 — 규칙 판단에 사진 원본은 필요 없다.

폼의 `required` 는 **거드는 것**이고 막는 것은 서버다 (§6.6).

### 🔴 부모에게 **걸기 전에** 말한다

이게 없으면 부모가 **찍을 수 없는 일**을 벌기로 걸고 아이는 올릴 방법이 없어진다 —
「동생에게 양보하기」 같은 것이 그렇다. 미션 만들기 화면에 적었다.

> 「벌기」 미션은 아이가 사진 한 장을 같이 보냅니다 — 집안일·심부름은 앱이 볼 수
> 없어서예요. 사진으로 보여줄 수 없는 일이라면 다른 영역으로 걸어 주세요.

### 왜 없는지도 말한다

어떤 칸엔 사진칸이 있고 어떤 칸엔 없으면 아이는 「왜 다르지」가 된다.

    잘 쓰기   "카드로 쓴 내역이 부모님께 보여요. 사진은 안 찍어도 돼요."
    모으기    "통장에 모인 돈이 부모님께 보여요."
    배워서    "내가 배우고 스스로 고른 실천이에요."

막힐 때도 「안 돼요」로 끝내지 않는다 —
「이 미션은 사진이 있어야 해요. **한 장 찍어서 같이 보내 주세요.**」

### 실제로 확인한 것

실 DB 에 다섯 종류를 만들어 봤다.

    EARN · 부모      📷 필수 — 없으면 「했어요」가 막힌다
    SPEND · 부모     사진칸 없음
    SAVE · 부모      사진칸 없음
    GROW · 부모      사진칸 없음
    EARN · 배워서    사진칸 없음

검증용 5건은 지웠다. `tester` 의 실제 6건 중 **사진이 필요한 것은 1건**이다.

### 뒤이어 — 벌기 「배워서 한 것」은 **선택**으로 열었다

위의 「남은 것」으로 올렸던 항목이다. 사용자 판단 —
*"사진 버튼 만들고, 지금 현재 있는것처럼 부모님한테 나중에 확인받기"*.

**필수로 올리지 않았다.** 같은 「앱이 볼 수 없는 일」이지만 **시킨 사람이 없다** —
아이가 배우고 **스스로 고른** 실천이라 증거를 요구할 자리가 아니다.
`FR-032` 의 「선택」이 그대로 산다.

    REQUIRED  벌기 · 부모가 준 미션    없으면 「했어요」가 막힌다
    OPTIONAL  벌기 · 배워서 한 것      안 붙여도 올라간다 · 부모가 나중에 확인
    NONE      잘 쓰기 · 모으기 · 불리기  칸 자체가 없다 · 왜 없는지 적는다

    photoRuleOf(topic, fromLesson)   →  아이 화면 · 서버가 같이 본다

🔴 **선택인 칸은 「안 해도 돼요」라고 적는다.** 필수와 같은 문구를 쓰면
   아이가 눌렀다가 막힌 줄 안다. *"보여주고 싶으면 붙여요.
   안 붙여도 부모님이 물어보고 확인해 주세요."*

🔴 계약 파일 뒷부분을 **한 번 잘라 먹었다.** 옛 블록을 인덱스로 잘라내면서
   그 뒤의 `MissionBoardView` · `CREATE_MISSION_MESSAGES` 까지 날아갔다.
   `tsc` 가 바로 잡았고 `HEAD` 에서 되살렸다 — **잘라내기는 지점을 둘 다 잡아야 한다.**

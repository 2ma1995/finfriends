# 핀프렌즈 SRS 저장소

**핀프렌즈(FinFriends) PRD v1.0** 을 **SRS 문서로 변환하고, 실행 가능한 태스크까지 분해**하는 작업 저장소입니다.

---

## 1. 작업 목표

### 1.1 하는 일

> **기준 템플릿은 `[SRS]AD-Core-Platform-Reference.md` 하나입니다.**

`[PRD]FinFriends-PRD-v1_0.md` 에 담긴 내용을, 예시 SRS 문서가 이미 쓰고 있는 **섹션 구성 · 표 스키마 · ID 체계 · 서술 톤**으로 옮겨 적습니다. 도메인만 다를 뿐(광고 플랫폼 → 아동 금융교육), 문서의 **뼈대는 예시 문서를 그대로 따릅니다.**

### 1.2 하지 않는 일

**ISO/IEC/IEEE 29148:2018 표준을 전부 만족하는 풀 스펙 SRS를 쓰는 것이 목표가 아닙니다.**

표준이 요구하는 전체 섹션을 빠짐없이 채우는 방향으로 문서를 부풀리지 않습니다. 예시 SRS가 다루지 않은 영역은 아래 1.3의 확장 규칙에 해당하지 않는 한 **쓰지 않습니다.**

### 1.3 확장 규칙

PRD에는 예시 SRS의 7개 섹션 어디에도 자연스럽게 들어가지 않는 내용이 있습니다. 버리지 않되, 임의의 형식으로 덧붙이지도 않습니다.

| 상황 | 처리 |
| --- | --- |
| 예시 SRS에 대응 섹션이 있음 | 예시 포맷 그대로 채움 |
| 예시 SRS에 대응 섹션이 없음 | **그 부분만** 29148 표준 구성에 따라 섹션 신설 |
| PRD에 없는데 예시 SRS에는 있는 항목 | 억지로 만들지 않고 미정으로 표기 |

확장으로 신설한 섹션은 **어느 표준 조항을 근거로 추가했는지 문서 안에 밝힙니다.**

### 1.4 승계한 제약 5항

입력 PRD가 명시한 제약을 SRS로 옮길 때에도 유지합니다.

1. **결정과 수치를 구분한다** — §4 기능 우선순위 · 규제 상수 · 범위 · ADR 8건은 **확정된 결정**이므로 확정 사양으로 옮기고, **기준선은 실측 전**이므로 목표값을 달성한 성과처럼 적지 않습니다.
2. **성능 · 가용성은 AC 역산 상한** — 확정 SLO가 아니라 *"이 값을 넘으면 해당 AC가 성립하지 않는다"* 는 상한입니다(ADR-007). 그 지위를 함께 적습니다.
3. **인용 금지 10항목** — PRD §9-2의 금지선을 그대로 승계했습니다(중립판 §1.4 ③). 특히 **「소비 순간 자동 개입」은 폐기된 기능**이며 로드맵에도 없습니다(ADR-002).
4. **미대응 상태 노출** — 사전 개입 사각지대는 계획 카드로 **부분 대응**이며 **자동 발동은 0개**입니다. 해소된 것처럼 기술하지 않습니다.
5. **등급 표기 승계** — `[A]` `[관측]` `[추론]` `[검증 대기]` `[설계 확정]` ✍️`[합성 가설]` 🧪`[모의]`

### 2.1 디렉터리 규칙

문서는 **역할별 디렉터리**로 나누고, 파일명은 `[분류]이름-v버전.md` 규칙을 씁니다. 공백과 한글을 파일명에서 뺀 이유는 **URL · 셸 · CI에서 이스케이프가 필요 없게** 하기 위해서입니다.

```
docs/
├── source-docs/       포맷 기준 예시 SRS
├── tech-design-docs/  기술 문서 — PRD v1.0 · SRS 중립판 · SRS 기술제약판 · 설계 다이어그램
├── plan-docs/         실행 계획 — 태스크 리스트 · 개발 실행 계획 · 압축 수행 일정
├── analysis-docs/     분석 — 추출 방법론 평가 · 축약 가능성 검토
├── ops-docs/          운영 — GitHub Project 설정 · AI 하네스 가이드
├── gtm-docs/          시장 진입 — 랜딩 퍼널 전략
└── tasks/             태스크별 이슈 명세 68건 (파일명 = 태스크 ID)

`docs/tasks/` 만 이름을 그대로 뒀습니다. 파일명이 이미 태스크 ID(`DAT-001.md`)이고, **등록된 GitHub Issue 67건이 이 경로로 매핑**돼 있습니다.

## 4. 입력 PRD 개요

- **제품:** 핀프렌즈 — *"배운 것을 실천할 자리를 만든다"*
- **두 가치 선언:** ① 아이에게 **성장이 일어난다** ② 그 성장이 보호자에게 **보인다**
- **북극성 KPI:** WPA(주간 실천 인정 아동 비율) — β 기준 ≥ 5/8 · 일반 공개 ≥ 55%
- **기능 범위:** F1–F18 · Must 8 / Should 5 / Could 3 / Won't 1 = **17건**
- **유저 스토리:** US-1 ~ US-8 · AC 26건 + 예외 AC 17건 = 43건
- **ADR:** 8건 (각 결정에 서 있는 가설 · 판정 실험 · 뒤집히는 조건 · 대가)

### 변환 시 유의점

PRD의 **결정은 확정**이지만 **기준선은 실측 전**입니다. SRS의 인수 기준에 수치를 옮길 때 확정 사양이 아니라 **실측 후 확정 대상**임이 드러나게 표기했습니다(중립판 §1.4 ①).

### 1–7장 — 예시 양식 준수

예시 SRS의 7개 장 구성과 요구사항 표 9열 스키마를 그대로 따랐습니다.

### 8–11장 — 29148 근거 확장

PRD가 이미 확정했으나 예시 양식에 대응 절이 없는 내용만, 표준 조항을 명시해 확장했습니다.

| 장 | 근거 조항 | PRD 출처 |
| --- | --- | --- |
| 8. 대상 사용자 특성 | §9.6.6 User characteristics | 페르소나 H1 · H2 |
| 9. 검증 | §9.6.19 Verification | WPA 조작적 정의 · AC 51건 · 실험 E1~E11 · 릴리즈 게이트 |
| 10. 가정 및 의존성 | §9.6.8 Assumptions and dependencies | 가정 A1~A5 · 의존성 D1~D6 · 리스크 |
| 11. 설계 결정 근거 | §5.2.8 Requirement attributes | ADR-001 ~ 008 |

### 수용 기준

**정상 32건 · 예외 19건 = 51건.** 전부 Given/When/Then 형식과 정량 임계치를 갖습니다. 예외 경로를 별도 절(§9.3)로 분리한 이유는, 예시 SRS가 인수 기준을 표의 한 칸으로 압축해 예외를 담을 자리가 없기 때문입니다.

### 12.2 축약 가능성 — `[Analysis]Task-Consolidation-Review.md`

**결론: 축약하지 않고 67건을 유지합니다.**

객관 기준(같은 Epic ∧ 같은 유형 ∧ 직접 의존 ∧ 복잡도 L/M)으로 **병합 후보 8쌍**을 전수 탐색했고, **0쌍을 병합**했습니다.

| 막은 이유 | 건수 |
| --- | :-: |
| 선행의 **후행이 많아** 병합 시 그것들이 함께 지연 | 5쌍 |
| **블로커**가 걸린 태스크(D2 · D5)를 Must와 묶을 수 없음 | 2쌍 |
| **우선순위·블로커가 달라서**(Must vs Could) | 1쌍 |

복잡도 `L` 4건도 흡수하지 않았습니다 — **작다는 것이 흡수의 근거가 되지 못합니다.** 담당자가 다르거나(콘텐츠·사업 담당) 규제 게이트·미결을 담고 있어 독립 추적이 필요합니다.

> **우리 이력은 축약이 아니라 승격이었습니다** — 65건에서 커버리지 검사가 REQ-FUNC-015·016 미담당을 지목해 **2건을 승격**해 67건이 됐습니다. 레퍼런스 사례(118→56 축약)와 반대 방향인 이유는 **처음부터 서버 진입점을 경계로 분해**해 과분해가 없었기 때문입니다.

병합 판정 기준은 **원칙 5가지**로 남겼습니다 — 후행 수 · 블로커 · 우선순위 · 담당자 · BE/UI 분리.

| :-: | --- | --- |
| 1 | 방문자 = 사용자 | **방문자(보호자)와 사용자(아동)가 다르다** |
| 2 | 전환 = 결제 | **전환 = 카드 연결** — 구독이 없다(ADR-005) |
| 3 | 가입이 시작 | **가입 후 7일이 진짜 시작** — 아이가 실천을 해야 작동한다 |

**가장 많이 새는 곳은 「진입 결정」**입니다. H2의 여정 감정이 그 단계에서 최저(1점)인데, 이유는
**현금은 5초인데 온보딩은 5단계**이기 때문입니다. 랜딩은 이 저항을 결정 전에 처리합니다 —
무료 · 나눠서 시작 · 카드 없이도 시작 · **「지금부터」 프레임**.

### 🔴 랜딩 문구에 적용한 제약

SRS §1.4의 **인용 금지 10항목**을 그대로 적용했습니다. 마케팅 문구는 여기서 가장 자주 깨집니다.

| ✗ | ✓ |
| --- | --- |
| *"소비 순간 알림이 갑니다"* | *"가기 전에 적고, 쓴 뒤에 맞춰봅니다"* — **자동 개입은 폐기된 기능** |
| *"아이가 성장했습니다"* | *"설계상 그렇게 되도록 만들었습니다"* |
| *"다른 앱은 확인 기능이 없다"* | *"확인은 됩니다. 그게 성장인지 알 수 없는 것이 문제입니다"* |

검사 결과 **금지 표현 0건**입니다.

### `web/service-example.html` 과 `app/` 은 다른 물건입니다

| | `web/service-example.html` | `app/` (§16) |
| --- | --- | --- |
| 목적 | **보여주기** — 링크만 열면 끝 | **개발의 시작점** — 화면 코드가 이어진다 |
| 실행 | 파일 더블클릭 · 빌드 없음 | `npm install && npm run dev` |
| 스택 | 단일 HTML · 인라인 CSS/JS | Next.js 16 · Tailwind v4 · shadcn/ui |
| 화면 | 3종 · 상태 6종 (같음) | 3종 · 상태 6종 (같음) |

**둘 다 남깁니다.** 제출·공유에는 HTML이, 개발 착수에는 앱이 필요합니다.
문구와 상태 정의는 **같은 명세(§16)를 원천으로** 하므로 갈라지지 않습니다.

### 라우트 13건

한 페이지에 화면을 나란히 놓는 모형이 아니라 **실제로 이동하는 앱**입니다.
동선이 없으면 인터뷰에서 *"아이가 어디서 출발해 어디로 가나"* 를 물어볼 수 없습니다.

| 보호자 · Clean | 아이 · Fun |
| --- | --- |
| `/consent` 동의 게이트 | `/child/home` 내 방 |
| `/parent/onboarding` 시작하기 5단계 | `/child/learn` 배우기 |
| **`/parent/tree` 성장 나무** | `/child/quiz/[topic]` 퀴즈 |

### 두 모드가 같은 토큰 이름을 다른 값으로 갖습니다

컴포넌트는 **자기가 어느 모드인지 모릅니다.** `data-mode` 를 다는 곳은 `ModeFrame` 하나뿐이고,
세그먼트 레이아웃이 그것을 부릅니다.

| --- | --- | --- |
| 본문 | **18px** | 15px |
| 모서리 | **20px** | 13px |
| 모션 | 별이 튄다 | **페이드만** |
| 캔버스 | `#FFF9F0` | `#FAF7F1` |

🔴 **`--ff-miss`(넘김·정체)는 두 모드가 같은 테라코타입니다.** 보호자 모드라고 빨강으로 바꾸지
않습니다 — 그 순간 조정 사실이 잘못으로 읽힙니다(P-03).

```
app/                              Next.js 16 · React 19 · Tailwind v4 · shadcn(base-nova)
  src/app/globals.css             듀얼 테마 토큰 26종 × 2모드 + @theme inline

`docs/ops-docs/[Ops]Goal-Prototype-Local-Visual.md` 가 `/goal` 자율 실행의 규범입니다.

**게이트만 두면 화면이 뜨기만 해도 통과합니다.** 실제로 라운드 2에서 그 일이 났습니다 —

그래서 게이트를 **세는 것**에서 **정의까지 보는 것**으로 넓혔습니다(v1.1).

### 이 프로토타입이 닫는 태스크는 없습니다

INF-001 · UX-001 · UX-002 · UX-004 · MCK-001 등에서 **시각 확인에 필요한 부분만** 떼어 썼습니다.
계측 · 테스트 · `prebuild` 게이트 · 배포는 범위 밖입니다(명세 §8).
